# Failed-cleanup recovery

The GUI and standalone MCP retain a shared Rust recovery object independently of the worker controller. Its phases are `starting`, `running`, `stopping`, `quarantined`, and `stopped`. Only `stopped` permits an explicit new Start. Recovery never starts routing, closes a target, changes permissions, or provides a force-clear action.

Assigned sessions capture original selected process identities before the supervisor starts a worker. Automatic sessions prewatch their explicit PID scope, but only an actual attachment attempt makes a target affected. The worker emits and flushes `Attaching` before opening the backend; the stdout reader records that attempt before forwarding it. Supervisor cleanup joins the reader before publishing a terminal event, including when it unwinds after a timeout. Duplicate attachment observations preserve the original process handle.

A successful terminal Stop clears recovery after worker exit and session resource cleanup. An acknowledgement timeout requests Stop and retains the controller in `stopping`; it does not claim cleanup succeeded. Failed cleanup retains the error and affected original process identities in `quarantined`, even if queued input is delivered later. Confirmed exit of every affected process permits an explicit new Start. If an original process could not be watched, an absent PID or conservative later watch is required; uncertainty keeps Start blocked. Unused allowed processes are excluded from the affected list. Profile edits cannot erase recovery state.

Standalone `routing_state.recovery` exposes `phase`, `error`, `targets` (`pid`, optional `application_name`, `status`, `affected`), and `can_start`. Target status is `running`, `exited`, or `unwatched`. The optional `application_name` is the executable basename captured once from the same original process handle during preflight, before the shared recovery lock is taken. It is display metadata only, never a process selector, and the captured name remains attached to that identity after exit. If the original process could not be queried, a watch is synchronization-only, or a watcher opens late after an initial miss, the field is absent and omitted from JSON; clients fall back to PID. Read-only inspection remains available after a terminal failure. An authenticated GUI-connected client can inspect the safe recovery projection for that GUI-owned lifecycle; after worker termination, the same connection is limited to recovery inspection and disconnect. See **GUI inspection continuation and explicit restart** below. Home offers **Recovery details**, opening the Ouroboros **Routing recovery** dialog, which lists each captured application name, PID, and existing affected-process status before the technical error. Missing names display as `Application {pid}`. The routing footer stays concise; matching retained technical detail is available in the dialog's default-closed **Technical details** disclosure. **Check recovery** is read-only; **Close recovery** dismisses the dialog. Start and app exit remain blocked while quarantined. A blocked GUI Quit or native window close reveals the existing recovery dialog; blocked Quit also restores a product-hidden or minimized window. Dismissing the dialog preserves quarantine. Ordinary Quit is permitted after the affected original processes exit.

## GUI inspection continuation and explicit restart

Same-controller authenticated clients may inspect after worker stop. Only existing `Inspect` and `Disconnect` are allowed; Stop closes worker commands and new connections. No endpoint, grant or worker retention is added. Projection has safe phase, `can_start`, and rows certified to the same connection and original identity. Rows require acknowledged policy for every active user and the original PID while its retained watch is known live; a certified row may survive exit on that connection. Filter stale or unproven rows before publication; omit raw errors, identity tokens and hidden counts. Inspection is read-only; standalone recovery is unchanged.

After affected originals exit, explicit GUI Start with a newly selected target retires the old broker, pipe and descriptor before creating a fresh controller. The Agent page resets; the user selects new scope and enables access, establishing a fresh descriptor, handshake and policy acknowledgement. `routing_stop` disconnects the local bridge client; the stdio MCP server may need normal transport shutdown separately.
