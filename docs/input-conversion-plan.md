# Mouse-to-key and keyboard remapping

**Status: bounded virtual acceptance passed.** Mouse-to-key and keyboard remapping are accepted for automatic concurrent routing to owned disposable x64/x86 applications. This does not establish hardware or broad application compatibility.

## Conversion contract

`Seat.output` is additive profile state. Its five mouse-button rules select exactly one of `Legacy`, `Key`, or `Disabled`; a key rule replaces that button's existing mapped mouse output. A bounded `keys` table maps source virtual keys to another key or to `Disabled`. In the MCP JSON object, `keys` uses canonical decimal virtual-key strings as property names (for example, `"118"`); duplicate or noncanonical strings are rejected by the request decoder. Source actions remain raw through recording and graph-category routing, then conversion runs for each destination before output claims are acquired. Synthetic Text packets bypass conversion. Mouse-origin key actions retain their source identity, device, action kind, code, scan code and extended flags for correct down/up pairing. Native key conversion accepts virtual keys 8 through 254 with canonical scan-code validation before any mutation.

Down ownership records the emitted destination key tuple. An up releases that saved tuple even if the mapping changes later. Native first-down/last-up union preserves holds when multiple origins produce the same key. Updating `OutputSettings` validates the whole candidate before changing it, and releases only affected conversion claims; macro, graph, manual and agent owners continue independently. Destination-local conversion does not rewrite the raw action used by other destinations. Output goes to the selected user's actual keyboard recipient, with recipient PID validation before queueing and delivery; hover alone does not select a target.

Non-default button output requires a virtual mouse. Any nonempty keyboard map, including a Disabled rule, requires a paired virtual keyboard. Physical mouse seats cannot use non-default conversion. The feature remains virtual-only and does not imply OS-wide key injection.

## UI and MCP

The Ouroboros **Output Rules** page exposes five source-button selectors, named-key entry, keyboard remapping rules, per-rule removal, a restore-legacy action, and separate profile-save/live-apply controls. It explains that key output goes to the currently selected keyboard recipient and requires a Legacy click to select/focus a target. Invalid names and missing virtual devices disable mutation controls with a visible reason.

The MCP `routing_output` tool is the 21st tool in current source. It has inspect and configure operations, distinct from `routing_settings`, whose complete cursor-settings replacement and whole-user release contract is unchanged. Output changes are acknowledged by the worker before the GUI commits them to profile state. Connected GUI agents may call `routing_output` Inspect read-only. Configure requires the existing explicit `AgentAccess.session_control` permission and passes the same permitted-active-user and authorized-PID checks as other live mutations; it does not widen either scope. The connected acceptance checks that policy and selected-recipient boundary.

## Focused acceptance

The independent [assessment](output-rules-assessment-2026-10-14.json) accepts the bounded virtual feature. Seven native groups cover conversion, first-down/last-up union, saved-up identity after live changes, source identity and raw graph recording, atomic rejection, and all five buttons mapping to distinct F5-F9 outputs. The original Ouroboros UI run records PASS for 35 actual control events, but only 34 are accepted feature controls because its original plain-Up Stop criterion failed; that historical result is unchanged. A corrected nine-control Stop supplement verifies plain Down/Up through v3 shutdown. Connected coverage consists of a 27-control prefix whose aggregate remains NOT ACCEPTED and a separate 20-control tail; five offline controls and two timeout cases complete the assessment. These actual step occurrences are not additive distinct-control counts. Earlier NOT ACCEPTED native, decoder, and connected aggregates remain preserved and were not relabeled. The decoder defect and its source fix are retained in the [failure record](output-rules-decoder-defect-2026-10-14.json) and [decoder checks](output-rules-decoder-source-checks-2026-10-14.json); the frozen source passed formatting, strict Clippy, all 108 workspace tests, and x64/i686 builds in the [producer record](output-rules-rust-checks-2026-10-14.json). Queue shutdown is accepted only for ordinary unfiltered message pumps. A pump that does not retrieve the fence, PM_NOREMOVE, or selected-range PM_REMOVE has no clean-stop guarantee; timeouts retain late Up normalization for the tested fixtures but do not prove safe session reattachment. See the [shutdown plan](queue-shutdown-plan.md). Physical devices, fixed-process assigned conversion, i686-controller behavior, general application/message-pump compatibility and broader Ultra parity remain unverified.
