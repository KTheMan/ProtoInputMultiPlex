# Web subscription capacity and real Core gap acceptance

`WebClient.refresh_subscription_with_capacity(capacity: u32)` lets a consuming application explicitly choose its event queue capacity for backpressure. Valid capacities are 1 through both authenticated `Ready.limits.max_queue` and Core `MAX_QUEUE` (4096). Validation happens before releases, callback fencing, model clearing, request ID allocation or socket send. Zero and out-of-range capacity return an error and leave the current subscription usable. Ready handshakes above the Core queue bound are rejected. JavaScript callers should supply an integer representable by u32.

The existing `refresh_subscription()` retains its authenticated default capacity, `min(Ready.max_queue, 256)`, and existing managed current-token lifecycle. A successful refresh releases this producer's held input, disables local production, fences pending virtual click pairing, and obtains a new atomic subscribed snapshot. Selection and input enabling remain explicit. There is no automatic resubscribe, reconnect or replay.

`request({kind:"click",user,button})` is legitimate typed virtual input. It now checks Live state, selected pointer user, local pointer enable, visibility and pointer control grant before admission. The server already checks the control grant; this closes a local default-off/selection contract defect, not a remote authorization bypass. Core atomically publishes exactly two button events. The Web client does not record a local held transition for atomic Click.

## Bounded acceptance group

The existing paired GUI acceptance controller keeps its original 17 correlated InputAtRevision cases. The separate gap group uses the same GUI Host, browser client, native observer and two GUI-created virtual users:

1. Disable pointer locally; Click must reject with unchanged state. Enable it explicitly. The next real native-correlated InputAtRevision Down must use the next request ID.
2. With that primary press pending in the virtual binding, reject capacities zero and advertised maximum plus one. Verify identical model and selection/enable gates. The next native-correlated Up must use the next request ID and complete the original callback pair, proving invalid refreshes neither queued requests nor fenced the pending pair.
3. Explicitly refresh at capacity one. Verify a new subscribed token, same two user/source identities and disabled local gates. Select/enable one user, then send/deliver one primary Down to establish a pending virtual pair.
4. Register a real public server callback and send one legitimate typed secondary Click. Core's atomic down/up necessarily overflows a capacity-one queue before HostBridge's post-command poll. Require the actual first Gap with the current token, `after_sequence` equal to delivered primary Down, and `lost_through` equal to the atomic secondary Up. Correlate both atomic events and the automatic primary cleanup Up with native source attribution. No lost input prefix may appear in Web stream notifications. Every captured Gap callback must observe cleared users/screens/windows/capabilities/mode and disabled selection/production gates. No pending primary callback may fire.
5. Click during NeedsSnapshot rejects locally without changing model. Explicitly call default refresh, which uses the managed current token. Verify a new token, snapshot floor covering automatic cleanup, the same identities and empty held buttons/keys. Ordinary virtual motion/Down/Up resumes for both users, each with exact native correlation and a matching callback release envelope.

The group separately counts nine InputAtRevision acknowledgments: two Down/Up operations around invalid-capacity rejection, one primary Down before overflow, and three motion/Down/Up operations for each of the two users after recovery. It also counts one atomic Click acknowledgment, one automatic-release acknowledgment and two explicit resubscriptions. The original counter remains 17. The controller marks runtime qualification only after actual checks succeed. One gap trigger and its cleanup may produce a second updated Gap; this is not presented as complete repeated-gap-family acceptance.

## Validation status and limits

This overlay is source-only and has not been compiled, formatted, parsed or run. Independent source review is required before integration. Root must later run the required Rust format/clippy/workspace test gates, build actual Rust/WASM/native artifacts from the integrated commit, and run paired acceptance on hosted Windows with those exact source/artifact hashes. Existing one-GUI/one-browser/one-native setup, private payload handling, exact origins, MCP status checks, normal Quit cleanup and timing bounds remain in force: native observation 60 seconds, native parent 90 seconds, controller 180 seconds, external process deadline 240 seconds.

Stale-token rejection and comprehensive repeated-gap-family acceptance remain open. No desktop-wide isolation, same-process multi-user isolation, physical input, injection or new feature-family claim follows from this group.

## Source review correction in overlay v2

Independent review found GAP-CAPACITY-001: v1 defined the gap group but omitted its invocation from `run()`. V1 is rejected and remains frozen. V2 calls `gap_cases(ids)` immediately after the original `hook_cases(ids)`, while the same browser and native observer remain live, before the native overlap wait and final disposal. The group issues its separate `status: PASS` receipt only after all checks. Before the public controller can set its final PASS, it requires that receipt with every flag and exact counts (nine InputAtRevision acknowledgments, one atomic Click acknowledgment, one automatic-release acknowledgment, two explicit resubscriptions), plus the original 17-case count and true gap qualification flag. Omission of the invocation now prevents controller PASS. This is a source correction, not runtime evidence. Rust bytes are unchanged from v1.
