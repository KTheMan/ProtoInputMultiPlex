# Independent app lifecycle acceptance plan

Status: preparation only. No app lifecycle implementation or independent result is accepted by this document. Launch only after the producer freezes exact images and transfers the exclusive test slot.

Use owned preferences/profile files, one disposable virtual x64/x86 target pair, one owned shortcut-conflict window, and a disposable startup-store location. Do not touch the user's Run key, hardware/RustDesk input, global input injection or unrelated window pixels. Preserve failed aggregates and complete only missing criteria in bounded tails.

| Group | Concrete acceptance evidence |
| --- | --- |
| Preferences and profile independence | Defaults and versioned document roundtrip through actual Settings controls and MCP. Invalid candidate/file preserves accepted preferences and file. A nontrivial seat profile survives preference edits; profile Import/Reset/Undo preserves app preferences. Compare complete documents, without replaying the contained native features. |
| Cold launch and window lifecycle | Launch minimized from an owned preferences path starts no routing or attachment despite saved PIDs. Actual Restore reveals the control center. Minimize/close-to-tray preserve the same GUI process/session; opting out makes normal Close exit. Record actual owned HWND visibility and process identity. |
| Tray actions and Quit | Open the real own tray menu and operate Restore, Pause/Resume, Stop and Quit using actual native controls/accessibility where available. One own virtual session demonstrates paused state, native key/button release, overlay destruction and broker/descriptor cleanup. A direct command alone is dispatch coverage, not proof of a tray menu click. |
| Shortcut registration and typed dispatch | Use real registration plus an owned conflict fixture. Rejected replacement preserves accepted shortcuts and preferences and unregisters any additions staged before the conflict. App-local typed hotkey messages exercise representative Stop, Pause/Resume, mode, routing-toggle and keyboard actions with unsupported/no-session guards. The seven supported actions are Stop, Pause/Resume, Toggle mode, Toggle routing, Switched, Concurrent and Toggle keyboards; do not multiply these into a cross-product of modes. GUI app-lifetime F11 remains registered across Stop; Quit frees it, verified with an owned registration probe that immediately unregisters itself. Physical-key delivery is outside this virtual gate. |
| Stop-to-Start handoff | In the same GUI, immediately after confirmed Stop completion, Start another own virtual session using fresh disposable target PIDs. Require real attachment/input and app-lifetime shortcut ownership retained. Stop and Quit cleanly release it. After GUI Quit, run one bounded standalone MCP Stop-to-immediate-Start check with fresh owned x64 targets and a representative plain key UP. Standalone session F11 must release before the Stop response so the next Start can acquire it. Do not use an arbitrary sleep as evidence of ownership transfer or reuse already-injected targets. |
| MCP permission and startup opt-in | App-preference mutation defaults denied and is independent of session-control permission. Explicit app permission grants only the documented operations. Agent permission alone cannot opt in to login launch. Actual GUI opt-in/opt-out changes only a disposable startup-store backend, with exact executable/path quoting and removal observed. Cold-invoking that command still starts no routing. |

Keep evidence to one finite document/provider group and one native/UI workflow, with exact image hashes, actual control events, native outcomes and an owned-process audit. Counts describe grouped behavior and control occurrences, not parity percentages. Existing shutdown timeout, output, graph, annotation and magnifier suites are not repeated.

Before authoring the runnable gate, settle the preferences-file CLI argument, app permission schema, disposable startup-store selector, tray window/menu discovery and actual menu activation route, shortcut action IDs, and truthful Stop/cleanup completion state. If actual menu activation or a provider effect cannot be observed, report that criterion unaccepted rather than substituting a direct implementation call or a telemetry-only assertion.

The source contract currently uses `--preferences <owned-file>` in GUI and MCP, GUI `--startup-test-key Software\\ProtoInputMultiPlex\\Tests\\<GUID>`, and standalone `--allow-app-preferences`. The test reads only that disposable registry key. The hidden top-level lifecycle class is `ProtoInputMultiPlex.AppLifecycle.v1`; only an HWND with the exact spawned GUI PID is eligible for callback or typed-hotkey messages. Its callback is `0x8051`, icon ID `0x5049`, and actual menu labels are `Open ProtoInputMultiPlex`, `Pause / Resume`, `Stop routing`, and `Quit`. A tray icon is required only while at least one launch/minimize/close-to-tray preference is enabled. No always-visible icon is assumed.

Menu verification uses the actual owned popup (`#32768`), its public HMENU and named native MenuItem accessibility action. The initial Python UI Automation provider attempt found an empty `comtypes` namespace and is retained as unaccepted environment/setup evidence. The available system MSAA provider is invoked through `AccessibleObjectFromWindow` and `IAccessible.accDoDefaultAction`, with ABI checked against the installed Windows SDK. Names/indices and process/thread/HWND ownership are matched to the real HMENU, and actual product effects must follow. This is MSAA evidence, not a UI Automation coverage claim. No global accessibility root or desktop/taskbar capture is used. A direct implementation command does not satisfy this criterion.

## Finite execution order

1. Run the standalone document/provider group without DLLs. Inspect defaults, verify explicit write denial and grant, roundtrip the complete document, reject invalid candidates and damaged/version/size-bound existing files, and exercise one actual Windows destination-replacement failure with a readable handle that denies rename/delete. Preferences/profile bytes and routing state remain independent; every failed save leaves no temporary file.
2. Launch the owned GUI minimized with a valid owned profile, injected disposable startup key and default Stop shortcut. Confirm no worker/overlay/broker, then restore by invoking the actual native tray MenuItem. Exercise a single real shortcut checkbox enable, invalid text with disabled Apply, correction, Apply and Revert; configure the remaining typed actions in one accepted candidate. Test local login opt-in/out against the disposable registry value and record its exact quoted command. Profile Import/Reset/Undo must preserve preferences; retain one safe preferences screenshot.
3. Start one owned virtual x64/x86 target pair. Establish plain F5/F6 holds, then fail a shortcut replacement through the actual Apply control using an owned registration collision. Preserve both native holds, accepted file and working original registrations; prove any earlier staged addition was rolled back using an owned availability probe. Minimize and close-to-tray retain the process/session. Actual menu Restore/Pause/Resume, representative typed mode/keyboard actions, separate connected MCP app-permission denial/grant and source-tagged preferences acknowledgements share this same session.
4. Actual menu Stop must yield plain native UP, destroyed overlays and removed broker descriptor. GUI app-lifetime shortcuts remain registered. Load a profile pointing to fresh owned targets and use the validated routing-toggle Start path, then actual menu Quit while holding a representative key. Native UP, GUI/window/icon/descriptor teardown and released shortcut registrations are required. Cold-invoke the recorded startup command only after the first GUI exits, from an owned working directory/profile, prove no routing, restore, and verify normal Close exits with close-to-tray disabled.
5. After GUI Quit, one standalone MCP Stop-to-immediate-Start check uses fresh owned x64 targets and one plain key pair. Require the Stop response before starting again, without a compensating sleep or reuse of injected PIDs. This covers the changed session-hotkey release boundary, not another input-family suite.
6. Add one focused failed-cleanup quarantine case: reuse only the owned no-pump/PM_NOREMOVE fixture from `scripts/test-output-shutdown-timeout.py`. A real Stop failure must remain visible, Home Start must be actually disabled, and the typed routing toggle must not start a worker while the exact old process is alive. This remains blocked even if the old pump resumes. Terminate that exact owned process, load a fresh owned target, and prove the guard clears through a real Start and representative delivery/cleanup. Do not replay the old fence timeout matrix or infer a successful Stop from a release received later.

Local application preferences remain editable during a ready session, subject to pending/stopping/quitting guards. A rejected registration or file replacement must preserve held input; stopping the session first would weaken that criterion. The startup store records only the disposable key's exact value type/bytes and cleanup; the real Run key is neither read nor written by this harness. Publication excludes bearer tokens, pipe names, unrelated inventory titles and private pixels.
