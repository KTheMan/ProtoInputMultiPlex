# Annotation desktop screenshots

Status: bounded virtual owned-fixture acceptance passed October 21, 2026. The [assessment](annotation-desktop-assessment-2026-10-21.json) and [independent GUI review](../runtime/annotation-desktop-ui-attempt008-review.json) cover one 55.531-second GUI/MCP family with two virtual users, disposable probes and a nonactivating known-color fixture covering all captured pixels. This acceptance does not establish broad desktop behavior or full Ultra parity.

The [public Draw workflow](https://www.mousemux.com/pages/manual/#draw) saves a screen image. This group adds that missing behavior with original Rust code and Ouroboros controls. Existing transparent-ink and selected-client exports retain their meaning and defaults.

Draw offers four explicit export choices: transparent ink, selected application composition, full desktop screenshot, and region screenshot. Desktop coordinates are physical pixels on the Windows virtual desktop, including negative origins. Full desktop resolves the current desktop extent at request time. Region requires an explicit positive rectangle entirely inside that extent. Both obey the existing 16-million-pixel export budget; unsupported geometry produces a visible error without publishing a file. Region values and export choices are transient UI state, not saved seat settings.

The existing `annotation` MCP tool adds `full_desktop` and `desktop_region` kinds. Only `desktop_region` accepts and requires `desktop_region` bounds; supplying bounds for another kind is rejected. There is no implicit desktop capture from an omitted field or an input PID allowlist. Historical requests retain their defaults. Results report the actual physical bounds, dimensions, ink scope and request-time document revision; historical metadata without bounds remains readable.

Connected agents use a separate **Allow desktop screenshots** permission, disabled by default. `ink_only` and `selected_target` exports require the existing capture grant; selected-target composition also requires the selected permitted target. `full_desktop` and `desktop_region` require the desktop screenshot grant instead, plus an authorized active user; `all_users` ink requires every active user's grant. The accepted policy case enabled desktop screenshots while target capture was false. The local GUI explicitly chooses the screenshot scope; standalone agents explicitly request a kind/region. Applying any Agent Access policy still revokes clients. The export lifecycle rechecks client authority, policy generation, user/roster, desktop extent and scope before publication. The desktop capability does not authorize input or other capture tools.

Ink is an immutable request-revision snapshot; background pixels are captured asynchronously afterward. Owned annotation overlays must be excluded from background capture so selected-user export cannot include another user's visible ink or blend ink twice. Existing cursor/magnifier exclusion is reused. A newly created annotation overlay attempts exclusion before presentation; publication is denied if visible ink cannot be excluded. Unsupported exclusion must not silently degrade screenshot semantics. Drawing remains usable when no screenshot is requested.

Use the existing retained asynchronous preparation/publication job, cancellation, deadlines and atomic destination publication. Invalid requests and cancellation before approval preserve existing destination bytes. As before, approval is the commit point; cancellation after approval is not rollback. Stop, disconnect and policy revocation keep their existing ownership rules. Do not replay uncertain export requests after a timeout without inspecting the destination.

The accepted group used virtual users and owned disposable windows only. A known-color, nonactivating fixture covered every captured pixel; no arbitrary user desktop was captured. Exact dimensions/bounds and decoded pixels were verified for selected/all-user ink, explicit full/region choices, target-grant-only denial, desktop grant, invalid geometry, preapproval revocation and normal cleanup. All 35 GUI steps and 12 scoped virtual-routing calls passed; formatting, strict Clippy, 419 workspace tests (0 failed, 3 ignored), and x64/i686 app-observer builds passed for the recorded source. These were acceptance tests, not a runtime-user fixture requirement. Attempts 001-007 remain FAIL, with their evidence and successful subphases unchanged. The historical missing exact pre-group source backup caveat remains.

This evidence does not establish arbitrary user or RustDesk desktop pixels, hardware input, mixed-DPI/multimonitor or display-driver breadth, same-process isolation, performance, a historical GUI stall cause or GUI reliability fix. Remaining drawing shortcuts, broader annotation workflows, P1 responsiveness and full Ultra parity remain open.
