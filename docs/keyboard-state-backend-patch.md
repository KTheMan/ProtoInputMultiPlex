# Native keyboard state compatibility

The Rust keyboard provider and host acknowledgement path passed [bounded native acceptance](native-keyboard-assessment-2026-10-20.json): an owned Win32 Ctrl+S accelerator plus two disposable classic WordPads with independent typing/focus, genuine Ctrl+S saves and normal Stop/close. This qualifies those sampled paths only; broader keyboard APIs, applications and isolation remain open.

The compatibility adapter is isolated in [0005-consumed-keyboard-state.patch](../patches/keyboard-state/0005-consumed-keyboard-state.patch), applied after the existing lifecycle overlay. The cumulative base and lifecycle patches remain unchanged. The backend build script removes overlays in reverse order for base verification and restores them in order. The matching host/target lifecycle build identity is `0x2026102000000001`, preventing an older resident backend from being treated as this build.

New behavior is Rust code. C++ forwards the original queue message, its actual removal status, final filter disposition and existing virtual mouse-button state. Rust maintains consumed keyboard state on the calling GUI thread, publishes it with `SetKeyboardState`, and supplies the synchronous `GetKeyState` and `GetKeyboardState` results. `GetAsyncKeyState` retains its existing behavior. `PM_NOREMOVE` does not advance or publish state. Removed physical messages that the existing filter blocks cannot become the virtual keyboard baseline.

The target provider is loaded from the architecture-specific cursor-observer DLL but has an independent lifecycle. Its operation does not depend on cursor-following settings or cursor observer Start/Stop. Native controls require the updated loader, a matching target provider and an existing supervised virtual lifecycle. Missing capability prevents input and reports an error. Compatibility focus retains its prior path.

The loader advertises `MuxKeyboardStateVersion() == 1` and forwards `MuxKeyboardStateCommand(instance, epoch, action, mapping, event)`. Its fixed-width 32-byte body contains `epoch`, reply mapping and reply event as three `u64` values, followed by action and reserved `u32` values. Actions are Start (1) and Stop (2). The target writes a status to the fresh four-byte reply mapping before signaling the event and closes its duplicated handles. A transport acknowledgement is required before enabling input. A partially transferred or timed-out command is not retried or considered clean.

Rust exports `ProtoMuxKeyboardVersion`, `ProtoMuxKeyboardStart`, `ProtoMuxKeyboardStop`, `ProtoMuxKeyboardMessage`, `ProtoMuxKeyboardGetKeyState` and `ProtoMuxKeyboardGetKeyboardState`. Status values are OK (0), disabled (1), busy (2), invalid (3), publication failed (4) and held keys (5). The existing lifecycle generation identifies the attachment; it is not assumed to increase numerically between workers.

Shutdown releases held input and drains remembered recipient queues while the provider remains active. A keyboard fence requires successful publication with no keyboard keys down on that consuming thread before acknowledgement. The host then requires a provider Stop acknowledgement before removing filters or preparing lifecycle retirement. Publication errors, outstanding callbacks, held keyboard state and uncertain remote handle ownership prevent clean reuse. Mouse-button overlays remain separate from keyboard-held accounting.

The ordinary queue-fence limitations remain: selected-range removal can overtake an earlier release, and attached input queues can share Windows keyboard state. No arbitrary message-pump, same-process multi-user or desktop-wide isolation guarantee follows from this implementation. Hardware and the RustDesk pointer are outside the current virtual test scope.
