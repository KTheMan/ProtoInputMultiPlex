# Additional official-feature dispositions

This supplement records capabilities named in the official [MouseMux feature comparison](https://www.mousemux.com/pricing/) and [manual](https://www.mousemux.com/pages/manual/) that lack a sufficiently precise status in the local parity matrix. The manual says it was updated August 11, 2026; pages were checked October 21, 2026. Statuses describe current local source/tracker evidence, not runtime acceptance. “Unassessed” means this review did not prove either implementation or absence. Licensing, vendor services/support, and imported MouseMux assets/code are not product requirements.

| Official capability | Local disposition | Evidence and limit |
| --- | --- | --- |
| Native / Disable / Emulate Ballistics, including startup calibration, Windows-version curves, speed and Enhanced Pointer Precision | **Partial** | Local UI explicitly describes per-packet response presets as “not Windows pointer ballistics” (`crates/protoinputmultiplex/src/gui.rs:6338`); the current parity row covers original per-packet curves and X/Y speed, not the manual’s named Ballistics modes (`docs/ultra-parity.md:26`). Official workflow: [manual, Ballistics](https://www.mousemux.com/pages/manual/). |
| Delta motion: detect external mouse movement and merge it into the app’s cursor coordinates | **Unassessed** | The official feature table names it. Local forwarding/replication and native cursor paths are distinct concepts; this audit found no acceptance record demonstrating external-motion detection plus coordinate merge. Do not treat input forwarding as equivalent. |
| Windows native cursor mode and virtual cursors surviving lock screen/UAC/secure desktops | **Unassessed** | Local cursor shapes, application cursor following and D3D presentation have bounded evidence, but no cited gate here proves these two official modes or secure-desktop behavior. A virtual cursor overlay is not proof of operation on secure desktops. |
| Core speed/thread-priority performance controls | **Unassessed** | The local P6 roadmap calls for two-user latency/resource measurement and GPU work (`docs/roadmap.md:24`); this is not evidence for equivalent user-facing core-speed or thread-priority settings. |
| Persistent base device mapping and keyboard restoration | **Partial** | The core device model persists a Raw Input interface path instead of an ephemeral handle (`crates/mux-core/src/lib.rs:31`), but current evidence does not establish the manual’s full per-device base-mapping and keyboard-restoration workflow. |
| Capture injected input from remote desktop and automation tools into a separate user | **Unassessed** | Local MCP `routing_capture` returns selected-target pixels (`crates/protoinputmultiplex/src/mcp.rs:1483-1497`); this is capture output, not input capture. No equivalence is claimed for injected-input tagging/capture. |
| WebSocket and native-language SDK interfaces | **Unassessed** | The repository tracks MCP workflows; this audit did not find acceptance or a contract proving those separate SDK transports. Do not imply MCP stdio is equivalent. |

Broader official groups already have disposition in existing rows and are not repeated here: RustDesk/Screen Matrix sharing (P8), multi-seat apps and browser integrations (P9), pen/touch/touchpad/gamepad adapters (P10), and GPU cursor rendering/performance (P6). Those rows remain planned or open at their stated priorities. This supplement does not move the roadmap: P1 reliability and P2 agent workflows remain ahead of P4–P10. Existing visible-unavailable states remain the rule until an unsupported control is implemented.

The official sources also describe user/device registration, role feedback, Switched versus Multiplex, and independent per-user configuration. Local switched/concurrent workflows have bounded acceptance, but are not broad hardware or application compatibility claims. No claim here upgrades a sampled UI workflow to full feature parity or says physical devices, secure desktops, arbitrary apps, or the official remote services were tested.

This is a documentation disposition, not feature completion. It introduces no new behavior, permissions, grants, or vendor dependencies.
