# Startup shortcut recovery contract

Initial application-shortcut registration failure now has bounded independent virtual acceptance. The lifecycle service remains available and opens the GUI visibly so the user can repair the saved set. Tray installation and native-window creation failures remain fatal. See the [assessment](startup-shortcut-recovery-assessment-2026-10-15.json) for the acceptance record and retained artifacts.

At startup, the service attempts the complete saved shortcut set as one transaction. If any registration fails, staged registrations are rolled back, the set remains inactive, and saved preferences are preserved. No action dispatches from a partial set. The GUI opens visibly even when **Launch minimized** is saved, shows **Shortcuts off** on Home with the error in its hover detail, and offers **Retry shortcuts**. Application preferences explains the inactive set and allows local edit/Apply; Revert discards only the draft. Start is disabled and rechecks full-set health before routing. No automatic retry or routing occurs.

Retry attempts the complete latest accepted shortcut set. Failure leaves it inactive. Apply stages and commits the complete candidate transactionally; a rejected or cancelled edit preserves the prior saved file and inactive state. An intentionally empty shortcut set is valid: once accepted it is active, no actions dispatch, and no shared emergency Stop subscription is required. Retry is rejected during a pending preference transaction; this denial is unit/source evidence, not a native observation.

Shortcut-set status and shared emergency Stop coverage are separate. The exact default Ctrl+Alt+Shift+F11 Stop binding uses the shared broker. A successfully accepted policy that omits that exact binding does not require the broker; a policy retaining the exact default still does. Native acceptance tested F10 Stop; intentionally empty sets have helper/unit evidence. If an active broker is later lost, existing shared-stop behavior requests ordinary session cleanup and reports unavailable coverage. UI Stop remains local. Native acceptance covers startup conflict and policy correction, not runtime deactivation or broker-failure interleavings.

Connected `app_preferences` may include `shortcut_status` from the live GUI lifecycle service. Standalone document replies use `shortcut_status: null` because the document does not own active registrations. This status does not independently prove broker health or target delivery. No MCP tool, permission, startup-registration control, or stopped-GUI bridge was added; a freshly inactive GUI requires local repair.

Acceptance passed two owned-conflict phases using local UI actions and disposable targets. The custom-chord phase verified visible startup despite saved minimize, whole-set rollback, failed Retry, successful full-set Retry after releasing the conflict, one no-input Start/Stop and a read-only connected Inspect. The default-chord phase verified rollback, inactive Revert, unchanged Apply rejection with saved bytes preserved, then explicit Stop-to-F10 and F8 Apply preserving unrelated settings and profile. No `routing_input` call occurred. Direct pixel review accepted Home at 360x360 and 320x360 and Application preferences at 480x560. These captures do not establish full-form visibility or PNG freshness.

The producer passed formatting, strict Clippy, 273 workspace tests, doctor and x64/i686 builds; x64 executed and i686 was built only. Raw phase records retain their pending labels; independent acceptance is recorded separately. The earlier zero-event setup and Clippy failures also remain preserved. Pending-transaction Retry and uncertain rollback remain unit/source evidence; live deactivation and file-save rollback are source-reviewed without injected OS-removal or timing faults. Accepted resources closed with no scoped survivors; worker evidence is stopped recovery/no worker/closed overlay, not a direct child exit-code sample.

Native-window/tray errors, malformed preference-file recovery, physical keys, hardware, RustDesk, arbitrary applications, desktop-wide or same-process isolation, broader P1 reliability, and full UX/Ultra parity remain open.
