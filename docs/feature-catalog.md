# Ultra feature catalog

This catalog turns MouseMux's public Ultra feature description into implementable Rust UI and service work. It records this checkout's state from the code and project evidence available on October 14, 2026. It is a planning baseline, not a claim of broad MouseMux parity or real-device compatibility.

Use three status words consistently: **Existing** means the core workflow is present in Rust and exposed in the Ouroboros control center; **Partial** means a narrower virtual, prototype, or UI-only version exists; **Missing** means no product implementation is present. A visible control counts only when its result is implemented. Keep unsupported features visibly unavailable until then.

## Product boundary

Recreate user-visible capabilities with ProtoInputMultiPlex's own Rust code, name, visual system and wording. MouseMux material is a behavioral reference; do not copy its code, icons, screenshots, application packages, or branding.

The target is product behavior. Paid edition caps, timed trials, activation, per-computer license rules, commercial-use permissions and priority support are vendor terms, not features to reproduce. Do not introduce artificial seat counts, session limits or license activation. MouseMux-hosted relays, app libraries, support, telemetry and update services are also not inherited capabilities. A replacement remote service or app catalog would need its own Rust implementation and an explicitly chosen service contract. Any bundled application, SDK or protocol implementation from a third party requires its own license review.

## Dependency and verification gates

Deliver the swaths in order, with these gates before moving outward:

1. **Foundation:** device identity and profile schema survive restart; disconnected assignments fail visibly; preview remains usable without ProtoInput DLLs. Test logic with virtual devices and disposable targets.
2. **Routing contract:** every input has an explicit seat and eligible process/window scope; mode changes, pause, stop, target exit and worker failure release held input and overlays. Test switched and concurrent behavior on x86/x64 disposable targets. Physical device tests are a separate acceptance gate, not inferred from virtual tests.
3. **UI truth:** every control either operates a working Rust service or is visibly unavailable with the dependency stated. Exercise each workflow using Ouroboros widgets and UI-local input; record which process/seat state changed.
4. **Input extensions:** the [10-check native settings run](settings-native-2026-10-13.json), [31-control UI run](settings-ui-2026-10-13.json), [19-control assigned-process smoke](settings-assigned-2026-10-13.json), [settings boundary run](settings-boundary-2026-10-13.json), and [clip-cache boundary run](macro-cache-boundary-2026-10-13.json) passed within their recorded virtual scope. See the [captured settings page](settings-control-center.png). The assigned smoke covers native curve, per-user held release, profile save and stop cleanup; it does not cover every message family. Re-run focused gates after related changes, then add physical-device validation independently.
5. **Macros, replication and graph:** the [native automation run](automation-native-2026-10-13.json), [32-step Ouroboros workflow](automation-ui-2026-10-13.json), [Macro Studio assessment](macro-studio-assessment-2026-10-14.json), stable-ID graph baseline, [advanced graph assessment](advanced-replication-assessment-2026-10-14.json) and [live-user assessment](virtual-users-assessment-2026-10-14.json) passed for their bounded virtual scopes; the focused settings/motion gates also passed as recorded in [validation](validation.md). Graph, Macro Studio and live-user evidence preserve earlier NOT ACCEPTED aggregate artifacts while recording separately accepted bounded tails/subgroups. The historical 18-tool live-user source passed its [producer checks](virtual-users-rust-checks-2026-10-14.json). Keep accepted claims within explicit owned targets, cooperative disposable applications and the actions enumerated by each assessment; validate hardware and broader application behavior separately.
6. **Remote and apps:** validate local lifecycle and identity handling with virtual sessions first; separately review the license and hosting/service contract for each selected integration. Do not claim sealed app isolation from window locking.
7. **Release readiness:** test profile migration, startup/tray lifecycle, mixed DPI, performance, accessibility and target exit/restart behavior. Publish app/backend compatibility limits before claiming general support.

Virtual-only checks establish policy and UI behavior. They do not establish physical HID behavior, same-process multi-user isolation, arbitrary application compatibility, remote-service quality or desktop-wide isolation.
