# ProtoInput Rust migration proposal

The selected A1–A3/B migration and Windows x64 release packaging are complete and independently approved as of November 6, 2026. The packaged app defaults to Rust for supervised entirely virtual workers. Conditional later ports remain deferred.

Favor a hybrid backend. Move the host-side loader and command transport into Rust first, while retaining the injected ProtoInput hook DLL, native injection helpers, and EasyHook. Make later ports conditional on a concrete reliability or maintenance benefit. Each stage must preserve the existing target permissions, recovery rules, and accepted input behavior.

The first deliverable is a checked, cancellable Rust control path for supervised virtual sessions. It should make connection and submission failures observable without changing target input semantics. It is not a proposed cure for the historical GUI stall: the [latest recovery contract](recovery-ui-native-poll-contract.md) still leaves that cause unresolved.

## Reasons for the proposed order

The upstream default branch still points to [dd29bf8d from September 15, 2021](https://github.com/Ilyaki/ProtoInput/commit/dd29bf8d22349605d0e1950c1c5dc4893d72670e), which is our pinned revision. The maintenance case is our local extensions and aging build dependencies; recurring upstream rebases are not the reason to migrate.

The clearest remaining weakness is the native loader's command boundary. [Loader.h](../vendor/ProtoInput/src/ProtoInput/ProtoInputLoader/Loader.h) sends commands synchronously and returns no error result. Legacy connection and injection paths can wait indefinitely. The newer [resident lifecycle overlay](../patches/lifecycle/README.md) already bounds startup waits for supervised virtual sessions and adds identity checks and retirement acknowledgements. Preserve those improvements.

Rust already owns routing policy, ownership arbitration, supervision, quarantine, and final cleanup commitment. Target-side cursor observation and consumed keyboard-state behavior are also Rust. Rewriting those again would add little value.

### Expected return and effort

The expected return is clearer failures, cancellable control operations, and ownership that is easier to review and test. No speed improvement is assumed. The host control port is a bounded integration project relative to the routing, provider, and supervision work already present, but its acceptance work is substantial: protocol compatibility, partial writes, handle ownership, restart, and both architectures must all be exercised.

Target lifecycle or input-state replacement is higher risk because it changes code running inside applications and interacting with native hooks. Rust's guarantees do not automatically cover foreign calls or raw-pointer contracts; those boundaries still require explicit invariants and testing. Windows DLL loader-lock restrictions also remain regardless of implementation language. See the [Rust safety boundary](https://doc.rust-lang.org/reference/unsafe-keyword.html) and [Windows DLL best practices](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-best-practices).

Leaving the remaining native backend in place has no automatic performance or stability penalty. The continuing costs are maintaining the native build/runtime and accepting existing opaque command failures until addressed. Those problems can also be fixed narrowly in C++; Rust is favored for host control because it consolidates ownership with the existing Rust supervisor. A full rewrite would spend compatibility effort on working mechanisms without an established return.

## Port A Host loader and command transport

### Boundary and ownership

Replace the loader-to-target control path. The GUI-to-worker transport in [session/transport.rs](../crates/protoinputmultiplex/src/session/transport.rs) is already Rust and remains responsible for its own queue, deadlines, and worker containment.

Keep the existing `Backend` facade where practical, with an internal implementation choice such as `NativeLoader` or `RustVirtualControl`. Select it before attachment and keep it fixed for the session. The native path remains the reference implementation and continues to serve physical and legacy routes during the pilot.

The Rust implementation must own every command for its attached targets: setup, hook/filter selection, admitted virtual devices, input, window selection, bounds, focus, freeze, cursor observation, keyboard provider, fences, lifecycle Begin, retirement, and connection close. Port only commands used by the supported virtual path; reject unsupported configurations before attachment.

Do not open a Rust-owned pipe and then call existing loader exports for that target. Those exports look up a separate native instance table and write through its pipe. There must be one connection owner and one serialized writer per target, with no per-command fallback between implementations.

### Work included

1. Add explicit Rust codecs for the existing native wire messages, including message IDs, field widths, enum and boolean representation, padding, and empty-structure sizes. Compare against C++ layout fixtures for x64 and x86. Do not serialize Rust's in-memory struct representation or uninitialized padding.
2. Create the existing lifecycle pipe before fresh injection. Preserve local-client restrictions, first-instance behavior, original-process identity checks, client PID authentication, namespace spelling, coherent readiness checks, and exact target build compatibility.
3. Launch the existing matching-bitness injector from an absolute runtime path. Preserve its unusual command-line contract: the helper expects the raw command line `PID 0`, without an executable-name argument. Use an explicit `CreateProcessW` application path and hidden launch, or a deliberately equivalent narrow adapter. A conventional `Command::args([pid, "0"])` is not equivalent. Keep helper descendants contained by the worker Job, and terminate/wait only owned helpers on timeout.
4. Implement serialized header/body submission, bounded queued work, explicit submission errors, and a single operation deadline that is not reset between the header and body. The existing receiver makes one read for each and fails on a short read. Preserve that contract: send the complete header and complete body in order, and retire the stream after a short or partial transfer rather than transparently retrying its remaining bytes. Stop must remain observable under backpressure. Prefer overlapped I/O with explicit cancellation; keep buffers, events, and handles alive until the operation has actually completed or cancellation has completed. Never free resources merely because a deadline elapsed.
5. Preserve the existing process leases, readiness checks, lifecycle Begin/Prepare replies, queue fences, cursor/keyboard acknowledgements, and all-target commit. Separate local transport state from permission to reuse a target.
6. Report enough metadata to distinguish connect, encode, write, target-exit, cancellation, and acknowledgement failures. Do not log typed text or introduce new product controls or agent permissions for this port.

For unchanged wire behavior, retain the existing target protocol and build identity. Do not rename existing named kernel objects. If the compatibility spike establishes that robust delivery needs a receiver read-exact loop, treat that as a separately reviewed compatibility shim with a changed target build contract and its own fault tests. Other target protocol changes belong to Port B and require a compatible new capability/build contract.

### Transfer and failure rules

Expose transport outcomes that distinguish failure before a write starts, completed submission, and failed or uncertain transfer after a write starts. None of these alone means that target configuration succeeded or input was consumed.

For commands carrying duplicated target-local handles, preserve the current conservative ownership rule: once writing starts, the host treats ownership as transferred, including after partial or failed writes. Do not cross-close possibly live target handles, replay a partially transferred command, or reconnect and resend automatically. A damaged stream is retired and the session enters the existing failure/recovery path. Any redesign of this rule needs a separate receiver protocol change.

Timeout, cancelled I/O, pipe closure, or worker termination must not mark cleanup successful. Only the existing complete acknowledgement and supervisor commitment sequence can permit reuse. Targets with uncertain state remain unavailable until their original processes exit, as specified by the [clean restart contract](clean-restart-contract.md).

### Delivery stages and acceptance

**A1 Compatibility spike:** implement codecs and test pipe/helper launch contracts against controlled fixtures. Confirm all commands required by the virtual pilot can be represented without native instance ownership. Stop here if the port requires broad target-side changes to deliver its stated benefit.

**A2 Virtual pilot:** run one supervised x64 virtual session against an explicitly selected owned target, then two targets. Exercise normal input, keyboard/cursor providers, selection, release, Stop, and clean reuse. Keep the native reference available for separate runs; never run both implementations against the same attachment.

**A3 Equivalent virtual support:** cover the current supported virtual command surface and both target architectures before default rollout. Exercise an i686 controller separately from x86 targets driven by an x64 controller. Compilation alone does not qualify runtime architecture support.

Acceptance must include:

- Cross-language layout/byte fixtures, short/fragmented-transfer rejection, and failed-write cases, including a controlled nonreading target pipe, EOF, cancellation, target exit, and Stop under backpressure. The native receiver's short-read behavior must be exercised; successful write-all retries are not an acceptance assumption.
- Handle-transfer tests showing no replay or unsafe remote closure after uncertain transfer; helper tests covering actual argument parsing, startup failure, timeout, and owned-child cleanup.
- Native reference and Rust runs on equivalent fresh fixtures, with genuine input counters, original-recipient releases, provider startup/shutdown, normal Stop, same-original clean restart where supported, and conservative quarantine on failed cleanup.
- Competing-controller rejection, stale identity/build rejection, and rejection before mutation for unsupported physical/legacy configurations.
- Measured input latency, resource use, and Stop behavior against the native reference. Agree regression limits before judging the candidate; do not assume a language speedup.

Likely code locations are new control/codec/transport/injector modules beneath `mux-windows`, integration in [protoinput.rs](../crates/mux-windows/src/protoinput.rs) and [lifecycle.rs](../crates/mux-windows/src/lifecycle.rs), plus the worker's backend construction. Reuse the ABI and native acceptance harnesses, extending them for this boundary. Keep changes to the vendored receiver out of A unless the spike identifies an essential, separately documented compatibility shim.

## Port B Command results and target lifecycle bookkeeping

### Favored scope

Start with explicit results for setup commands whose current `void` path conceals failure. Define request identity, target generation, command result, and native error reporting. State exactly what each result certifies: accepted configuration, successful hook operation, provider readiness, or another bounded action. A write receipt is never an application-delivery receipt.

Use fixed-width versioned messages and target-local reply objects or another explicitly designed return channel. The existing command pipe is outbound from the host; it cannot simply be treated as a bidirectional channel. Negotiate the capability and exact resident build before use. An incompatible or missing capability rejects the operation before mutation.

Only then consider moving target-local validation, reply ownership, and lifecycle transitions into Rust if this removes concrete duplicated bookkeeping. Host leases, quarantine, target authorization, and final all-target commitment are already Rust and remain there.

### Native work retained

Keep actual hook installation/removal, native callback quiescence, native state reset, and focus-loop pause in native adapters. The existing receiver serializes commands with native packet state. A Rust reducer must share that authoritative boundary; it must not create a second command reader, independent mutex, or parallel copy of state still mutated by native hooks.

Preserve `Pending` host commitment, target `Prepared`, and eventual `Reusable` as distinct facts. Partial failure must remain non-reusable. Do not promise DLL unloading or physical-session restart.

### Acceptance and decision gate

Require fixtures for partial configuration, hook failure, stale generation, duplicate request, lost reply, EOF, pending callbacks, and failed retirement. Verify rollback or conservative quarantine after each relevant partial failure. Re-run normal/restart/provider behavior on both architectures. Adopt this scope only when the added results resolve a chosen failure-reporting gap; migrating the full native lifecycle is a separate decision.

## Port C Input conversion and filter decisions

Move pure transformations first: validated input fields, coordinate conversion helpers, synthetic key/button state transitions, and filter decision calculations. Reuse existing Rust settings and routing types rather than duplicate policy inside the target DLL.

Keep Win32 hook entry points, message retrieval/removal, actual message posting, and native API forwarding initially. Replace one authoritative state owner at a time. A reducer may compute a decision while a native adapter performs the OS operation; both implementations must not independently update the same input state.

Choose each extraction alongside a specific feature or defect. Preserve recipient selection, scan codes, wheel signs, side-button tags, press/release ownership, and `PM_NOREMOVE` behavior. Compare with the reference on native message-pump fixtures, including selected-range retrieval, ordinary removal, nonremoval, and nonpumping targets. The [queue-fence limitation](queue-shutdown-plan.md) requires semantic work and testing; translation to Rust does not remove it.

Defer wholesale replacement of `RawInput.cpp`, `MessageFilterHook.cpp`, focus handling, and fake-cursor state until a smaller extraction demonstrates value.

## Port D Physical devices and Raw Input registration

Keep discovery and stable device-path persistence in their existing Rust implementation. Resolve transient Raw Input handles immediately before attachment. The later port would extend the Rust command path to physical selections and, where beneficial, move device-admission bookkeeping into Rust.

Retain registration interception and native packet capture until tests establish exact registration ownership and restoration behavior. Initially preserve fresh-target-only behavior for physical/legacy sessions. Do not inherit virtual restart claims or change global input locking.

Begin only with two actual mice/keyboards and disposable applications available for unplug/replug, changed handles, simultaneous input, held releases, target/controller exit, failed attachment, and Stop tests. Cover both target architectures and record which controller architectures actually ran. Hardware timing and application compatibility cannot be qualified by virtual packets alone.

## Port E Existing Rust cursor and keyboard providers

Continue the present design: narrow native interception forwards original target facts to the Rust provider. Rust owns image resources, associations, consumed keyboard state, and provider lifecycle. See the [cursor bridge](cursor-observer-backend-patch.md) and [keyboard provider](keyboard-state-backend-patch.md).

Extend these providers for a specific missing API or observed application case, with native tests of that case and existing lifecycle behavior. Keep `GetAsyncKeyState`, shared input queues, cursor visibility semantics, and broader keyboard layout/API coverage explicitly scoped to the implementation and its tests. This row has no standalone rewrite milestone.

## Native components to retain

Retain EasyHook's detour/trampoline machinery, instruction relocation, thread filtering, and assembly. Retain required matching-bitness injector/proxy implementations and minimal dependency bootstrap. Keep unused upstream XInput/DirectInput, handle-renaming, and other optional hooks outside the migration scope until product work needs them.

A defect in one primitive can justify replacing that primitive. Neither C++ nor Rust has an assumed performance advantage here. Removing all C/C++ dependencies, building a new injection engine, and supporting independent users within one process are separate projects.
