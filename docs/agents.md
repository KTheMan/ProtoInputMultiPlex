# Agent interface

Optional [GUI callback activity](gui-activity-contract.md) is available in supporting builds through stopped `profile_setup` operation `activity`, or live `routing_state.agent_session.gui_activity`. It observes callbacks without granting input, capture or recovery authority. Compare fresh samples in the same authenticated GUI lifetime; missing or incoherent data is unavailable, and callback returns do not prove rendering or application input delivery.

GUI startup first displays a responsive initialization window. Wait for the Dashboard before enabling Setup or live Agent Access. A preferences failure shows its path and cause; repair that file and use Retry in the same window. Startup does not grant MCP authority or replace unreadable preferences with defaults. See the [startup contract](gui-bootstrap-contract.md) and [bounded assessment](gui-bootstrap-assessment-2026-10-28.json).

`protoinputmultiplex mcp --runtime <absolute-runtime-directory>` serves MCP over stdio using the official Rust SDK (`rmcp`). It exposes the same Rust routing policy, native delivery worker and overlays as the Ouroboros UI. It owns a separate session; it does not connect to a running GUI session. Routing servers expose 23 tools, including application-preference inspection/configuration under a separate permission boundary.

The [typed Input Mapper assessment](input-mapper-assessment-2026-10-29.json) accepts
a bounded private x64 foundation after 657 passing tests, 26 UI actions and 50 SDK
calls against two separate owned virtual targets. Follow the
[Mapper contract](input-mapper-contract.md): inspect and validate, Apply disarmed,
explicitly Arm, verify effects, then Disarm and confirm cleanup. This accepts the
recorded parameter edit/own-ACK and representative ownership workflow; broader
GUI authoring, native payload magnitudes and on-disk profile reload remain
unverified here. It does not approve the current Rust port, same-process
isolation, full Mapper/Ultra parity or a historical GUI-stall P1 fix.

For stopped GUI profiles, choose **Settings → Agent access → Agent Access → Enable setup access** and use its private descriptor with `mcp --gui-connection <descriptor.json>`. This separate connection exposes only `profile_setup`: Inspect, discovery refresh, whole-profile Configure, and Save/Load/Import/Export at GUI-selected paths. Start is GUI-owned and retires Setup authority before controller creation; setup access never grants live routing permissions. Use the current revision and resolve local drafts before mutations. See the [workflow and file-result limits](stopped-setup-contract.md) and [bounded composed assessment](stopped-setup-assessment-2026-10-27.json).

Stopped `profile_setup` also supports `configure_persistence` for the two
startup-load/save-on-Quit preferences. It requires opt-in Setup authority, the
current revision, and both booleans in `persistence`; it cannot choose paths or
load immediately. The ordinary `app_preferences` Configure schema does not accept
these fields. See [profile persistence](profile-persistence-contract.md) for the
payload, completion/cancellation rules and startup/Quit behavior.

For the optional live GUI path, start the MCP server with `mcp --gui-connection <descriptor.json>`. Open **Settings → Agent access** after routing is Ready, choose active virtual users and eligible target PIDs, then enable access. After the matching policy acknowledgement, **Copy MCP server entry** prepares the exact GUI executable and three arguments as JSON; **Copy descriptor path** copies only the locator. These controls remain unavailable while the session or broker is unready. **Additional permissions** starts closed, with separate Applied grants and differing Draft permissions summaries. Capture and session changes remain explicit permissions. Keep the descriptor private and never copy or publish its contents. The [bounded compact handoff assessment](agent-connection-handoff-assessment-2026-10-21.json) covers sampled layout, draft separation and read-only connection; OS clipboard contents, clicked feedback and visible one-client count remain unverified. The [scope contract](gui-agent-plan.md) and earlier [access assessment](gui-agents-assessment-2026-10-14.json) retain their separate evidence limits.

Agent Access startup and retirement now use a retained background Rust owner. Wait for the matching enabled-policy acknowledgement before connecting; after disabling or stopping, wait for cleanup and obtain the current descriptor when re-enabling. Stop intent is not terminal cleanup. The [bounded lifecycle assessment](gui-broker-lifecycle-assessment-2026-10-21.json) composes an observed normal x64 virtual workflow with a later read-only absence audit; original failed raw runs remain preserved. The historical GUI stall remains OPEN/P1. No tools or grants changed.

Build the application and native backend using the root README. Configure your MCP client with absolute executable/runtime paths, for example:

```toml
[mcp_servers.protoinputmultiplex]
command = 'E:\.cargo\target\debug\protoinputmultiplex.exe'
args = ['mcp', '--runtime', 'E:\Kenny\Documents\GitHub\ProtoInputMultiPlex\runtime']
```

Adapt those paths to your checkout. This example is documentation; the project does not edit your global MCP configuration. Protocol output goes only to stdout; native loader output is captured inside the disposable worker. SDK protocol negotiation supports current and compatible older MCP clients.

Standalone application-preference writes need a separate explicit opt-in. For a controlled document, add `--allow-app-preferences --preferences <absolute-test-document.json>` to the `mcp` arguments. Omit the flag for read-only Inspect. The write scope is the selected preferences document; it does not start the GUI, initialize tray/hotkey services or update login startup.

Connected `app_preferences` may include `shortcut_status` from the live GUI lifecycle service; standalone document replies use null because the document does not own active registrations. This status does not independently prove shared-broker health or target delivery and adds no tool or grant. After a saved shortcut conflict, repair locally through Home **Retry shortcuts** or Application preferences. See [startup shortcut recovery](startup-shortcut-recovery-contract.md).

Standalone `routing_state.recovery` reports `phase` (`starting`, `running`, `stopping`, `quarantined`, `stopped`), `error`, affected `targets` (`pid`, `status`, `affected`), and `can_start`. Target status is `running`, `exited`, or `unwatched`. An acknowledgement timeout requests Stop and retains the controller in `stopping` until a terminal result. After terminal failure, the controller is released but shared recovery retains original affected-process identities until exit; unused allowed PIDs are excluded. Read-only inspection remains usable. Wait for `can_start`, then explicitly Start with fresh authorized targets. Profile changes and late input delivery do not clear quarantine. Recovery is process-local memory, with no durable restart guarantee, force-clear, kill-target, or automatic routing action. A GUI connection reports `recovery: null` because its lifecycle belongs to the GUI; compact Home offers **Recovery details**, **Check recovery**, and **Close recovery**. See the [recovery contract](failed-cleanup-recovery-contract.md) for coverage and limits.

## Assigned release recovery

In concurrent assigned sessions, `routing_state.users[].pending_releases` counts failed held-token UPs, not all holds or client owners. Other routing modes report null when this count is unavailable. Saved releases retry on their original recipient at a 250 ms minimum retry interval; process exit retires those obligations without UP. No new DOWN, replacement window or PID grant is generated. Inspect held keys/buttons and each user's status after a rejection.

A typed local/standalone `InputRejected` completes as an error without ending the worker or waiting for a cursor State tick. Connected clients retain their existing tagged Agent errors and connection. Rejected release-dependent settings stay uncommitted; a local GUI draft may remain edited. Home's pending-count button opens **Input release details**; **Release all input** attempts cleanup for every virtual user. A connected client's `routing_input` action `release_all` remains client-scoped. Failed Stop still quarantines all originally assigned processes until exit, followed by explicit fresh-target Load/Start. No tool or permission was added. See the [assessment](assigned-release-recovery-assessment-2026-10-15.json) and [contract](assigned-release-recovery-contract.md).

## Explicit window selection

For deterministic root selection, call `routing_input` with `action: "select_window"`, `user`, `pid`, `hwnd`, and the exact `eligibility.creation_token` string from `routing_windows`; do not reconstruct the token or identify the target by title. Selection is passive and transient. The worker commits selection before replying; the MCP server internally matches `WindowSelected` and returns worker state. The client receives no raw event or selection request ID. Inspect selected PID/status. **Current application** is committed worker state; **Highlighted** is a draft. Connected GUI clients need user/PID grants, an allowed session PID, and **Allow session changes**; capture is separate. Applying Agent Access revokes all existing clients: reconnect and Inspect under the new policy before further use. There is no public grant bypass. Before lazy attachment, the server captures the recipient for the first key DOWN and each text action; key UP uses its saved recipient. Text can be partial on error; inspect state before retrying. See the [contract](explicit-window-selection-contract.md) and [bounded assessment](explicit-window-selection-assessment-2026-10-16.json).

## Native application controls

For automatic desktop routing with a virtual mouse/keyboard pair, opt-in `keyboard.application_focus: "native_controls"` preserves native control focus/capture behavior. It is separate from `keyboard.focus` recipient lookup and `keyboard.enabled` source enablement; Compatibility remains the default. Standalone `routing_start.initial_keyboard` accepts one complete keyboard object per user in `users` order; omission preserves defaults and wrong arity is rejected before worker creation. Configure the GUI session while stopped; connected clients retain existing grants and cannot use standalone Start.

Live `routing_settings` replaces the complete acknowledged object and must preserve `application_focus`. Policy changes are rejected before held-input release or settings mutation, including while paused or unattached. Stop and configure a new session to change policy. Recipient snapshots remain candidates, not delivery proof; target mouse capture is distinct from screenshot capture permission. No tool or grant was added (23 tools). The [contract](native-controls-contract.md) and [assessment](native-controls-assessment-2026-10-19.json) accept a composed two-process x64 virtual workflow, including focus persistence/Tab, capture isolation and GUI/standalone Stop. The intermittent GUI stall remains OPEN/P1; broad compatibility and full UX/Ultra parity remain open.

## Clean stop and virtual-target reuse

`routing_windows.windows[].eligibility` is a read-only snapshot (`pid`, `creation`, `state`, `reason`); it does not reserve a target, attach, or acknowledge input delivery. Only a `reusable` eligible target can be reused by a virtual-only supervised session after the prior all-target commit. Direct CLI and physical/legacy sessions remain fresh-target-only. Failed or ambiguous cleanup keeps touched targets quarantined until the affected original processes exit. This adds no MCP tool or permission. See the [contract](clean-restart-contract.md) and [bounded assessment](clean-restart-assessment-2026-10-15.json).

The default `Ctrl+Alt+Shift+F11` emergency Stop helper can be shared by multiple standalone MCP desktop sessions and the GUI only when they use the same executable path, metadata and version on the same Windows logon and desktop. Supervised standalone automatic-desktop/concurrent routing acquires an independent lease before worker spawn; direct CLI attach and nonconcurrent assigned routing retain existing behavior. GUI subscription requires accepted preferences enabling the default binding. The emergency event stops all subscribed participants; GUI Stop, each standalone `routing_stop` and EOF remain local. Custom chords remain exclusive and the default chord is reserved for Stop. For GUI-connected agents, use the GUI exact binary and preserve per-client grants and input ownership; the helper adds no MCP tool, permission or global agent-trigger capability. See the [contract](shared-emergency-stop-contract.md).

For a target-selection Busy/dirty denial, `routing_input` may return a processed acknowledgement (`isError: false`, `running: true`) while `routing_state.users[i].status` begins `Routing unavailable: ` followed by that target's eligibility reason. This exact denial path produces no held input, capture, or native output. This acknowledgement does not prove input delivery; inspect status, selected target, capture and held state, then reconcile before further input. Do not blindly retry or replay. Other `InputRejected` paths have their own results.

Recovery views are process-local, while dirty markers on touched/versioned virtual targets survive controller restarts until the original target exits; there is no on-disk recovery state.

If the helper loses coverage, the existing `routing_state.last_error` reports the loss and the helper requests ordinary Stop. Inspect running/recovery state and do not replay interrupted input. The GUI disables Start while its default binding lacks coverage. **Retry emergency stop** obtains a healthy lease; an accepted preference change may instead remove or replace the shared default binding. Start checks health again when that binding is enabled, and a pending preference transaction blocks Retry. See the contract for failure behavior and limits.

## Motion coalescing

In `routing_settings`, `settings.motion_coalescing` has optional `buffer_events` (2-64) and `interval_ms` (1-16). Both `null` means immediate output; either configured limit flushes first. Count-only uses a 16 ms oldest-event deadline; timer-only has a 64-event cap. Windows scheduling can exceed a deadline. Preserve the complete cursor settings object when replacing it. The Motion page exposes the same settings; foreground/high-DPI filtering is unavailable for virtual input. See the [contract](motion-coalescing-contract.md) and [bounded assessment](motion-coalescing-assessment-2026-10-15.json). No new MCP tool or grant is added; current count remains 23.

## Application preferences

`app_preferences` takes `operation: "inspect"` with no settings or `operation: "configure"` with the complete settings object (`launch_minimized`, `minimize_to_tray`, `close_to_tray`, and `shortcuts`). In standalone MCP mode, Inspect reads the selected preferences document. Configure writes only that document, and only when the MCP process was explicitly launched with `--allow-app-preferences`; this does not start the GUI, register hotkeys, alter the startup Run key, or change `launch_at_login`. Pass `--preferences <absolute-path>` for a disposable document during tests. The schema rejects unknown fields, including `launch_at_login`.

Current source also accepts optional `appearance_mode` (`dark` or `light`) and `zoom_percent` (50–200 inclusive, in multiples of 5). Omitted appearance fields preserve their current values, so existing Configure clients retain the selected theme and zoom. Legacy version-1 documents default to dark/100%. The GUI stages these changes until Apply succeeds; a larger zoom may grow a window to its minimum usable size. This presentation batch is implemented and awaiting its independent runtime gate.

With `--gui-connection`, Inspect requires enabled Agent Access. Configure additionally requires the distinct **Allow app-preference changes** grant in the currently acknowledged GUI policy; it does not inherit `session_control`. The GUI services the request and acknowledges the saved state. In either mode, `launch_at_login` in the returned document is the persisted preference, not a readback of the Windows Run key. Only a local GUI Apply can change the current user's startup registration after explicit opt-in. The startup command uses absolute executable/preferences paths and must fit the 260-character UTF-16 limit. Lifecycle tests use an injected disposable registry provider under `Software\\ProtoInputMultiPlex\\Tests\\`; they must never write a user's real Run key.

The 23-tool discovery/schema record by itself does not establish application lifecycle behavior. That behavior passed a separate bounded independent assessment ([lifecycle assessment](app-lifecycle-assessment-2026-10-14.json)); the compact Home and grouped Settings navigation also passed a separate presentation assessment ([presentation assessment](application-presentation-assessment-2026-10-14.json)). Neither establishes full Ultra UX parity, actual logon/reboot behavior, hardware behavior or broad application compatibility. Do not cite previous 420×600 Home evidence as acceptance of the revised size.

## Optional connection to the running GUI

Standalone `mcp --runtime` behavior remains available and unchanged. With `--gui-connection`, MCP connects to the dashboard's existing supervised session rather than creating another routing session; do not call `routing_start` in this mode. The shared connection permits virtual input for selected active users, current-state access, read-only inspection, and capture of an explicitly selected target when the GUI owner enabled capture. Agent Access starts with capture and session-level changes disabled. Session-level changes cover cursor settings, output configuration, routing mode, pause and resume; `routing_output` Inspect remains read-only, while Configure requires the existing explicit session-level permission and passes the same active-user and authorized-PID checks as other live mutations. Other unsupported live mutations return an explicit unsupported-operation error. Mode changes apply only to automatic desktop routing and require the policy to include every active user. Pause and mode operations are global and can release GUI-owned programs and held input. `release_all` and `routing_stop` release only the connected agent's ownership; `routing_stop` disconnects the agent while GUI routing continues. Legacy composite automation and the numeric-index `routing_replication` tool remain standalone-only. Connected annotation PNG export uses the capture grant, not the session-change grant. It requires an authorized active user; `all_users` ink additionally requires every active user, and selected-target composition requires that user's currently allowed target. Ink is an immutable request-revision snapshot. Preparation and publication run off the input thread, while the MCP request waits for its final result; the GUI exposes `export_pending`, and a second connection can route input during the job. Composition captures only the selected client window. The [bounded export assessment](annotation-export-assessment-2026-10-15.json) accepts permission-denial checks, selected PNG and target composition, F5 routing from a second user while pending, and a magnifier-export smoke test. Native precommit revocation, retained capacity under revocation and explicit normal Stop remain unverified; source/unit evidence is separate. Connected stable-ID graph and virtual-replica operations use the existing tools and are described below.

Connected `annotation` Configure and ClearUser additionally use **Allow session changes** and an authorized active virtual user. ClearAll and configuring an all-user clear shortcut require permission for every active user. Configure rejects held input touching that user, open strokes and consumed activator/shortcut keys; it does not release another actor’s claims or cancel programs. Clear changes ink only, so a consumed activator still needs its matching up. A pre-existing all-user shortcut also checks the current all-user/session-control grant after input translation. Successful replies carry the actual annotation ACK and authoritative settings into the Agent profile and GUI Draw editor. The [independent assessment](connected-annotation-assessment-2026-10-14.json) accepts bounded virtual MCP/GUI workflows, including unrelated-user hold preservation and cleanup; mapped/replica combinations, pending races and retired-clone cases have source/unit limits. Connected annotation PNG export passed the bounded scope described above. Approval is the file commit point. After an approval timeout, inspect the destination before retrying; Stop/crash after approval can interrupt publication and leave temporary-file cleanup incomplete. The native run did not establish the precommit-revocation, retained-capacity or normal Stop timing behavior listed above.

Connected `magnifier` Configure/Refresh/Export passed [bounded independent acceptance](connected-magnifier-assessment-2026-10-14.json). Off Configure needs session control; enabling needs session control and capture plus the selected allowed target. Refresh and Export require capture independently of session control. Accepted settings synchronize the Agent profile, stored virtual-user seats and Ouroboros editor. Export uses a bounded asynchronous encoder/writer with reauthorization before commit and at completion; a valid cached frame remains usable during a newer refresh. A timeout after approval may still leave a published file. Desktop capture stays unavailable through the connection. See the [command and export contract](connected-magnifier-plan.md) for authority, retry semantics and precise evidence limits.

`routing_capture` captures only the selected target window through the existing capture path. Its GUI policy is off by default and limits target selection to the explicitly allowed PID set. Captures are single-flight on the routing worker, limited to 16 megapixels and a 2 MiB PNG, with a five-second response deadline. Acceptance decoded a 3979x3986 owned-client image (15,860,294 pixels; 321,034-byte PNG) and measured native F9 input from another seat while the large capture/reply was outstanding; input took 47 ms and capture/reply took 5.109 seconds. This fixture measurement is not a latency guarantee. Provider-hang timeout retention remains untested. The returned image is scoped to a target window; this is not general desktop reading. The PID policy authorizes native target focus, capture and click/gesture input; it is not cursor confinement. Unfocused virtual movement may position the cursor, and the subsequent click is checked against the target policy. GUI recorders do not record input sent by connected MCP agents.

The GUI connection uses a local named pipe protected by the current logon SID and a private descriptor. Transport allows up to eight concurrent clients, with the configured active-user list providing the separate seat limit. Requests and idle connections have 50-second deadlines. One GUI controller owns the broker for the session; disabling access or stopping the session closes it. Disconnecting an agent releases only that agent's input ownership and leaves GUI routing running. The independent assessment passed six substantive evidence groups and 37 actual GUI control occurrences across 21 labels on one x64 GUI controller with cooperative x64/x86 targets. It preserved three earlier NOT ACCEPTED prefix artifacts (15, 17 and 22 controls); accepted evidence does not change those results. It does not cover x86 controllers, assigned-process GUI-agent mode, forced provider hangs, cross-logon/remote clients, client-capacity overload or crash-time descriptor deletion. Successful product Disable/Stop cleanup was exercised; runner cleanup after a failed attempt is not product behavior. See [the assessment](gui-agents-assessment-2026-10-14.json) for exact coverage and limits.

`routing_start` can accept optional `user_ids` in user order and an optional version-1 `graph` to restore. Omit both for ordinary generated users with paired virtual keyboards. `routing_state` reports each user's stable `id` and name plus the graph definition and revision. Existing profile seats whose ID is exactly empty receive a deterministic ID derived from their persisted mouse interface path when normalized and saved. Explicit IDs are immutable identity keys across device, name and order changes; graph edges refer to IDs rather than current numeric positions.

`routing_settings` is a complete per-user replacement: omitted fields take the documented `CursorSettings` defaults rather than retaining that user's previous values. The server parses the whole object, validates ranges and unique button outputs, and validates the user index before requesting any worker mutation. The response and `routing_state` expose the last acknowledged settings. Motion curves (`linear`, `gentle`, `strong`) shape each relative motion packet before axis speed and inversion. The five source buttons are ordered primary, secondary, middle, back and forward; each may map to one unique output or `null` to disable it. The legacy `swap_buttons` option composes after that custom map and swaps only primary/secondary outputs. Back and forward remain separate outputs unless explicitly mapped. Wheel axis defaults to vertical; horizontal input can be ignored (default), converted to vertical, or preserved with its own scale and inversion. Preserve passed bounded virtual acceptance in automatic mode and concurrent assigned routing; fixed mode without a virtual cursor rejects it. See [the assessment](horizontal-wheel-assessment-2026-10-14.json). This does not establish hardware behavior or general application scrolling compatibility.

`routing_input` key actions use a named key string: ASCII letters/digits, F1–F24, Numpad0–Numpad9, modifiers, navigation keys and named punctuation. Key mapping uses the active Windows keyboard layout. Use `action: "text"` to type Unicode text instead; text is validated as a complete action before the worker is called, supports up to 4096 UTF-16 units, and permits newline and tab among control characters. It does not use the clipboard. Unicode submission requires the native input transport v2; an older backend reports that text support needs a rebuild.

Automation is session-local. Recording captures actions issued through this agent's virtual users; it cannot observe physical or global desktop input. `automation_record` with `recording: false` finalizes the clip. `automation_clip` accepts `action: "inspect"` or `action: "load"` plus a version-1 clip object. Clips store ordered relative-microsecond actions (`packet`, `move_to` or `text`) and are validated against the session's user and keyboard assignments when loaded. Playback events are remapped to the destination user's virtual devices. `automation_play` returns after command acknowledgement; use `routing_state` to monitor the playback state. Legacy `automation_cancel` is a global session command: it cancels the synchronized composite program and all Macro Studio user programs, then releases their held input. Use `macro_studio` cancel to stop just one independent user lane.

`routing_replication` remains the compatible numeric-index operation. Each edge names zero-based `source` and `target` users and may select `mouse`, `keyboard` and `text` categories; omitted categories default to `true`. It rejects duplicate, empty-category, invalid-user and cyclic graphs without replacing the prior graph or stopping the session. Graph replacement is rejected while legacy composite or Macro Studio recording/playback is active, preserving those programs. Replicated packet input is remapped to the destination user's virtual mouse or keyboard.

`routing_graph` accepts flattened `inspect`, `apply` and `cancel` operations. An edge may add `options` with `motion`, `wheel`, `horizontal_wheel`, `buttons` in primary/secondary/middle/back/forward order, `position` (`anchored` or `source_relative`), signed `offset_x/y`, `click_delay_ms` (0–60000), and `step_interval_ms` (0–1000). Missing options preserve legacy anchored, immediate behavior and allow all mouse components. Source-relative positioning uses the processed source user's position plus offset; anchored hops preserve the destination anchor while forwarding displacement. Chains compose hop by hop and diamond conflicts choose a canonical stable-ID path independent of edge order. Step interval is temporal pacing, not gain: the first discrete event is immediate, later events are spaced, and motion is coalesced with a final snap barrier. Compound mouse packets remain unsupported by inherited packet validation.

Connected `virtual_users` Inspect is read-only. Start and Stop reuse the existing tool and input schema, with `expected_revision` from Inspect required for connected mutations. They require current session-control permission, automatic desktop routing with a nonempty fixed PID allowlist wholly covered by Agent Access, permission for every active virtual user, and permitted current mouse/keyboard recipients. Start also validates the selected source and target. It appends a session-only stable user and source-to-clone edge, but does not expand Agent Access: the new user appears unchecked. To send input to it or replicate through it, select it in the existing Agent Access page, apply the policy, reconnect because applying the policy revokes connected clients, then Inspect before writing again. Until granted, direct input and graph paths involving the new user are rejected.

Stop normally requires permission for all active users and removes only a generated user. The sole narrower user-scope exception is a connected client stopping the exact clone it created while that client remains connected; the other active-user and PID checks still apply. Disconnect, EOF or policy revocation clears that creator receipt but does not remove the clone. Clones and graph edits remain owned by the GUI session and are not persisted into stopped profiles. Preflight rejection preserves graph, queue and held input. An authorized native cleanup failure can occur after some cleanup has already happened; inspect the roster and state before retrying rather than assuming rollback. The connected lifecycle implementation is complete, but its [bounded independent acceptance](connected-virtual-users-assessment-2026-10-15.json) passed five groups, 18 actual GUI observations, 19 named outcomes and three original frames using three distinct x64 targets; see the [connected replica contract](connected-virtual-users-contract.md) for exact scope and limits.

Apply validates endpoints, destination keyboards, categories, options, path bounds and cycles before replacement. Optional `expected_revision` compare-and-set rejects stale Apply without changing the graph, queue or held input. The scheduler caps combined event/motion jobs at 4096, estimated payload at 8 MiB, and cadence reservations separately at 4096; `routing_state.automation.replication` reports pending counts/bytes, event/payload limits, suspension, error and emitted/coalesced/cancelled counters. Cancel clears pending copies and replication-owned holds while preserving graph definition/revision and ordinary/source-program owners. If admission fails, the triggering source action is rejected before source-target delivery; release cleanup is delivered for a source release. Overflow suspends copies, but ordinary source input continues without replication until valid Apply resumes routing. The offline Ouroboros editor offers staged options, selectable nodes/wires, undo/redo and user-chosen graph JSON paths (4 MiB limit, 64 history edits).
