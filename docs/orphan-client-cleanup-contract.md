# Disconnected-client input cleanup

An authenticated GUI client owns its saved input releases independently of its pipe. EOF, connected Stop, or a valid policy replacement immediately revokes that client's authorization and creation receipts. The worker stops its recordings, playback and queued copies across every user, then attempts every matching saved input owner even if an earlier release fails. Other clients' and manual owners of a shared token remain held. Failed final owners retain their original saved Up; retries never replay Down, text or programs.

An `Ok` routing return alone does not complete the final owner's release: desktop routing can report failed delivery in route status while returning `Ok`. Cleanup checks that the routing engine no longer reports that token held before deleting the last owner. A still-held token returns a pending-release error and remains retryable. This checks local routing ownership, not an arbitrary application's receipt of its queued Up.

The worker retains a cleanup obligation until cancellation succeeds with zero saved owners. After the normal router tick reconciles target exits, it retries at most one due client, rotating fairly with a 250 ms interval per failing client. A failed release is not discarded because of a retry count or elapsed time. Active clients and pending cleanup together share the existing eight-client admission capacity; a retired client's slot becomes available only after cleanup completes. Existing authorized clients can continue routing while new connections are backpressured.

A policy candidate is validated before mutation. Once a valid policy is installed, both authorization layers reflect it and every old client is retired, even when a release fails. Pending cleanup does not grant permission to execute commands, inspect as the old client or reconnect using its identity. Saved release cleanup remains available after a policy is narrowed or disabled. Terminal session failure still uses the separate [process-identity quarantine](failed-cleanup-recovery-contract.md).

`agent_runtime::State.cleanup`, the GUI script's Agent Access snapshot, and connected MCP `routing_state.agent_session.cleanup` expose rows with `client`, `pending_owners`, `attempts`, and `last_error`. Owner count means saved source-owner obligations, not native keys; several owners may share one held token. Errors are bounded to 512 characters. Passive updates report owner/error changes and completion rather than every identical retry; attempts are the count at the observed snapshot. Compact Ouroboros status stays above the scrolling permission form, with a real **Last release error** disclosure and **No agent cleanup pending.** when clear. Its separately identified scroll region is limited to 180 points and 45% of available height; client-specific disclosure IDs preserve independent rows. Passive status cannot acknowledge a local policy draft or cancel a command deadline.

Connected `routing_stop` confirms disconnection, not completion of all native releases. Observe the GUI or another already authorized client's inspection for pending cleanup. No impersonation, manual force-clear, automatic reconnection, new public MCP tool or additional target grant is provided. This state is session-local memory, not durable across worker/application restarts.

The native gate covers EOF with a vanished child HWND in an otherwise live owned process, exhaustive cleanup of another user, preservation of another client's shared hold, process-exit reconciliation, continued input and normal Stop. A separate eight-click/four-Execute visual gate shows pending client/owner count, retry/error and clear status at 680×620. Earlier rejected images remain rejected; the pinned layout does not diagnose the observer/screenshot mismatch. Transient live-target Up retry and policy-failure consistency use production Engine/coordinator tests. Neither the process-exit fixture nor those tests prove arbitrary native provider recovery, physical-device behavior, same-process isolation or full P1/Ultra parity.
