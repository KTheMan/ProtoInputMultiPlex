# Assigned release recovery

Concurrent assigned routing retains a held token only after successful native DOWN submission. UP uses the saved user/device/identity/window. Failed UP validation or submission retains that ownership; the worker retries only saved UPs with a 250 ms minimum interval. This is best-effort scheduling, not a latency guarantee. An original pinned process watch confirming exit retires its tokens without delivery. An unavailable child HWND while the process lives is not process exit; no replacement recipient is selected. Submission success is not proof that an arbitrary application consumed input.

All-user cleanup visits every token despite failures. Required keyboard-focus, settings and Pause releases complete before their corresponding state commits. Resume contains per-seat target/publication failures so healthy users can continue. New invalid DOWNs do not create native held bookkeeping. Failed Stop still attempts every user and removes hooks, then uses the existing conservative quarantine of all originally assigned processes. Their exit is required before an explicit fresh-target Load/Start. There is no force-clear, kill-target, automatic restart or permission expansion.

Assigned concurrent `State.pending_releases` is the count of failed held-token releases, not all holds or logical client owners. It is null in modes that do not expose this count. Held keys/buttons and route status remain inspectable. Home shows a compact pending-count button with **Input release details** as its accessible/hover name. The Ouroboros dialog lists affected users/counts, a bounded cause and **Release all input** for every virtual user. Long cause text is ellipsized; the full status remains available on hover. Terminal events close this dialog and hand lifecycle recovery to the existing recovery workflow.

Only typed `ReleaseFailure` becomes transient local/standalone `InputRejected`: it updates the error, completes a negative ACK immediately without waiting for a State tick, clears GUI busy and keeps the session live. It is not replayed to later subscribers. Release-dependent settings remain uncommitted; GUI drafts may remain edited. Connected MCP preserves existing tagged Agent error replies and grants. Its `release_all` remains client-only. Scheduled tap failures retry only their saved UP; background errors are not command ACKs. Other errors retain their existing handling.

The [independent assessment](assigned-release-recovery-assessment-2026-10-15.json) accepts one owned x64 virtual integration run: A's original EDIT child is destroyed while its root/process lives, failed key/button UPs remain pending, settings reject unchanged, B survives exhaustive cleanup and Resume, failed Stop releases B, both original PIDs remain quarantined until exit, then actual fresh C/D Load/Start/normal Stop succeeds. Focus/settings/Pause/exit transitions additionally have source/unit evidence; transient successful native retry is not forced in this gate.

Physical devices, native x86 execution, fixed-relative native recovery, arbitrary applications, HWND reuse, forced races, durable quarantine, same-process isolation, GPU/performance and full Ultra/UX parity remain unverified or open. No hardware/RustDesk/OS-pointer input, unowned pixels, startup registration, new agent tools or new permissions were used.
