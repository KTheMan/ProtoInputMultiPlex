# Application lifecycle and preferences

The bounded lifecycle gate passed. The [independent assessment](app-lifecycle-assessment-2026-10-14.json) covers application preferences, tray and shortcut actions, connected-agent preference permissions, isolated startup registration and cold invocation, truthful cleanup failure/recovery, and standalone session handoff. The frozen source passed formatting, strict Clippy, 135 workspace tests and x64/i686 builds in [producer checks](hidden-lifecycle-rust-checks-2026-10-14.json). The compact Home and application presentation passed separately in the [presentation assessment](application-presentation-assessment-2026-10-14.json); neither establishes complete MouseMux UX or Ultra parity.

## Implemented behavior

Application preferences are stored separately from routing profiles and load before the GUI window is created. The local GUI controls launch/minimize/close-to-tray behavior and seven typed shortcut actions through an app-lifetime tray/hotkey service. Launch-at-login is an explicit local opt-in. Starting the app never starts routing or attaches PIDs from a saved profile. MCP can inspect the persisted login preference but cannot change it or write the startup registration. The `app_preferences` MCP Configure operation requires a distinct explicit permission in standalone and GUI-connected use.

The GUI services lifecycle and session events from eframe's background `logic` pass, so Restore can be processed while the viewport is hidden. Hotkey and Home actions share validated routing paths. Shortcut updates stage registrations before saving; collisions or save errors preserve the accepted binding, and failed startup-registration writes restore the prior registry value. Startup tests used an injected disposable provider. Stop and Quit wait for acknowledged cleanup. If cleanup fails or times out, the error stays visible and affected targets are quarantined until safe recovery; the app does not report them as stopped.

## Scope limits

Acceptance used owned virtual targets and a disposable startup provider. It did not write the user's real Run key or validate actual logon, logoff or reboot behavior. Physical-device behavior, general application compatibility, hardware/global input injection, desktop-wide or same-process isolation, and full Ultra parity remain unverified. Session shutdown receipts cover ordinary unfiltered message pumps; selected-range `PM_REMOVE` retrieval may overtake a queued release and remains outside the guarantee. A timed-out or failed cleanup requires restarting the affected target before reuse. See [validation](validation.md) for the wider evidence record.
