# Ultra parity reference refresh — October 29, 2026

Official pages accessed **2026-10-29**: [manual](https://www.mousemux.com/pages/manual/), [SDK overview](https://www.mousemux.com/pages/sdk/), and [AI agents](https://www.mousemux.com/ai-agents/), including the overview's linked Windows/Web SDK documentation. These establish capability targets, not evidence that our implementation supplies them. No vendor assets or implementation code were copied.

Our accepted loopback **Command SDK** provides scoped Rust/browser command access to an existing GUI authority, with bounded ownership, idle, revocation and cleanup acceptance. It is not full Windows/Web SDK parity. The compact Access/SDK UI group is still under its own checks and acceptance. Neither that UI nor a successful command workflow completes Ultra parity or approves the parallel Rust port.

| Reference capability | Verified local boundary and tracking consequence |
| --- | --- |
| The manual distinguishes a **Windows message SDK** from a **WebSocket Web SDK**. The linked [Windows SDK documentation](https://www.mousemux.com/pages/sdk-windows/) describes application input reception and control through registered Windows messages. | `crates/mux-sdk-client/src/lib.rs` exposes command `tools/list`/`tools/call`; backend Windows input delivery is not an application-facing event SDK. No equivalent developer input-subscription interface is established by the accepted command gate. External automation is already tracked, but native application integration needs an explicit separate requirement. The linked Windows manual is labeled V2, so its version-specific contract must not be silently asserted as current V3 behavior. |
| The [Web SDK documentation](https://www.mousemux.com/pages/sdk-web/) covers per-user/device event handlers, element-relative coordinates, unified input handling, virtual users, and window/coordinate forwarding. | Our actual browser acceptance invokes command tools against owned targets; it does not qualify a multi-user DOM/canvas event-consumer library or its coordinate mapping. Dedicated web/app integration remains the existing **P9** gap. Keep these requirements distinct from authenticated command transport; no automatic fallback or proprietary protocol compatibility is implied. |
| The [AI agents page](https://www.mousemux.com/ai-agents/) describes a typed Input Mapper: vector, scalar and binary signals; processing/gating/transforms; screen reading through OCR/image matching; and LLM nodes. Graph inspection/construction and armed execution are separate capabilities. | `mcp.rs:282` applies `replication::Definition` or `forwarding::Definition`. Those `mux-core` models describe stable user-to-user edges, filters, offsets and cadence, not general typed operator ports or a screen-reading/provider graph. Existing macros, capture, replication and forwarding are useful accepted slices. **P2/P5 currently track broader agent/automation and graph work, but typed processing, OCR/image-match and LLM-node capabilities need explicit gap entries**, rather than treating the existing `routing_graph` tool as equivalent. |

**Suggested next coherent feature group after compact UI acceptance:** a typed processing-graph foundation for existing virtual mouse/keyboard sources and outputs. Define an original versioned schema with compatible ports, deterministic bounded evaluation, a small useful transform/gate set, and matching Ouroboros/MCP inspect/edit/apply controls. Reuse current explicit grants and off-by-default actuation; make cancellation/revocation release only the correct ownership. Establish one bounded owned-virtual end-to-end contract before adding vision or external-provider nodes. This is a proposed P2/P5 slice, not authorization to implement it today or to pull P9 browser integrations/P10 device adapters forward.

[Roadmap priority](roadmap.md) remains unchanged: **P1 reliability is OPEN**, and its historical cause is unresolved. Same-process independence, physical-device breadth, remote collaboration and arbitrary applications retain their existing separate gaps in [the parity matrix](ultra-parity.md). The vendor's sealed containers are described as future work, not a shipped baseline to claim. Scope completion must follow capabilities and evidence, not a node-count target. This refresh changes requirements documentation only; no Rust, tests, app execution or active UI scope changed.
