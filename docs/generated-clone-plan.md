# Live generated-user lifecycle

## Bounded virtual acceptance passed; broader compatibility remains open

The Rust worker supports adding and stopping session-only virtual replicas through the Ouroboros **Virtual Replicas** page and the `virtual_users` MCP tool. The [independent assessment](virtual-users-assessment-2026-10-14.json) passed for automatic desktop routing with explicit owned target PIDs and cooperative x64/x86 applications. It records five native groups (one setup and four behavior groups) and 35 actual GUI control occurrences across a 26-control prefix and nine-control cleanup tail, covering 19 distinct labels. The 26-control prefix's original aggregate remains NOT ACCEPTED; its accepted controls and the separate cleanup tail support the assessment without relabeling that artifact. The actual [page capture](virtual-users-control-center.png) shows the Start/Select/Stop controls and generated roster. Producer checks also pass formatting, strict Clippy, 87 workspace tests and x64/x86 builds in [source verification](virtual-users-rust-checks-2026-10-14.json).

The flow is available only in an automatic desktop routing session. GUI target selection is an explicit choice from eligible windows already covered by the current routing policy: a nonempty PID allowlist is honored, and an empty GUI list retains the existing unrestricted policy without adding scope. MCP routing sessions require a nonempty explicit PID list, and `virtual_users.start` attaches only to the explicitly selected PID on that list. Both frontends require an active source identity and use worker acknowledgements with a roster revision check.

Each successful clone appends a new stable seat ID and virtual mouse/keyboard paths to an append-only session roster. Its cursor settings are copied from the source and initialized at the target client center. Annotation and magnifier settings are Off/default, and its macro lane begins empty. The clone gets one source-to-clone graph edge with the selected per-edge filters, position, offset and timing options. Starting or stopping a clone does not trigger a global held-input release.

Stopping a clone creates an inactive tombstone; its index and generated device IDs are not reused during the session. The worker removes graph edges incident to that clone, cancels queued copies and replica-owned claims that cross the clone boundary, and leaves unrelated users' owners and source input intact. Original seats cannot be stopped through this lifecycle. Generated seats are removed from the GUI's in-memory profile when the session ends and are not saved in stopped profiles. MCP snapshots retain inactive slots for the duration of the session so indexes remain stable.

If a release fails, the clone stays active at the same roster revision. Stop
can be retried while the session remains healthy. Some releases and cancellation
may already have taken effect. [Clone Stop assessment](clone-stop-retry-assessment-2026-11-06.json)

The native registration exports are void and provide no per-device removal/acknowledgement call. Virtual IDs stay reserved until worker exit. If clone setup fails before its slot is published, no mutable roster entry is exposed, but any allocated ID remains reserved. A target that exits during setup must likewise leave no active slot. Restart injected targets before another routing session.

## Verified scope and limits

The accepted behavior includes explicit owned-target attachment and center initialization; source settings copied to the clone; virtual F5/Back/text/movement delivery; atomic scope/source/revision/name/options rejection; tombstone/index safety; cleanup of delayed crossing replication, clone-owned held inputs, annotation ink, Macro Studio state and overlays; profile omission; and controller EOF cleanup. GUI evidence verifies actual Start/Select/Stop actions, acknowledged roster changes, delivery to owned x86 EDIT controls, scoped removal, a later unique slot, and profile Save/Load cleanup. Root's independently inspected [page capture](virtual-users-control-center.png) shows the tested controls and live roster.

This acceptance does not cover hardware or RustDesk input, an i686 controller, assigned-process cloning, same-process isolation, arbitrary applications, remote operation, full Ultra parity, forced native allocation/provider failure, or crash recovery. The accepted runs exercised default motion options and one delayed chain; they did not enumerate every optional clone edge setting or checkbox combination. Inactive-user tombstones and rejection were checked, but every disabled control on other pages was not clicked independently. The UI prefix's original aggregate remains NOT ACCEPTED because its last Stop sample expected a telemetry file to clear; the separate cleanup tail directly verified resource destruction and profile cleanup. No claim is made that Stop rewrites or clears that last routing telemetry file.
