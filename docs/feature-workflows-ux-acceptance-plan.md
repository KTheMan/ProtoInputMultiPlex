## Acceptance criteria

- The baseline and candidate use owned A/B virtual-user fixtures and explicit owned working directories; the completed baseline has `feature-ux-baseline` IDs, while the candidate has `feature-ux` IDs plus synthetic keyboardless/physical-user fixtures. Treat the baseline as a geometry reference only. Record executable and source hashes, x64/i686 producer records, screenshot PNG hashes, original verdicts, actual Script event receipts, `ui.output.page.json`, `ui.profile.navigation.json`, `ui.profile.json`, and output ACK records. i686 build evidence does not count as execution.
- Baseline frames are render references only: its normal Output frame begins at a lower-form viewport and its minimum frame is not proof that the content was scrolled to every endpoint. Candidate normal and 320×360 Output/Profiles frames and the representative Settings frame come from the product's own `ui.png`, match measured client geometry/DPI for the launched GUI PID, are fresh after resizing, and are independently reviewed from original PNG bytes. The final evidence set reuses four unaffected originals from the first offline run and substitutes the two post-fix minimum frames; the first-run Profiles/Automation minimums remain preserved as superseded originals. Capture the final Macros & replication frame only after the client is measured at 320×360 and the disabled `Apply replication` action is reached. The layout phase separately proves the top legacy action controls and named selectors are reachable at the same width. Do not infer usability from image dimensions alone.
- Keyboard steps must report focus on the requested visible/enabled control. Tab must advance through the intended controls and Enter must activate the intended action; a mouse click receipt cannot substitute for these observations. Keep this bounded to the Output Discard action and the Profiles Save action. On Profiles, Tab requests and measures 320×360 without saving a frame; Enter activates Save profile, and the one Profiles minimum PNG is captured only after file/snapshot equality and visible Save completion status.
- An invalid named key produces a visible validation error and a visibly disabled commit action, with committed profile bytes and worker ACK count unchanged. Valid but unadded source/destination text also keeps Save/Apply disabled and remains in the editor until Add or Discard. After Add, the mapping becomes staged; a valid button key becomes a draft only. Discard returns the selected user's complete draft to the acknowledged profile value and leaves the other stable-ID user's draft/profile unchanged. Saving to profile mutates in-memory profile state only; Save profile writes it durably; Load restores that exact saved output after an intervening in-memory edit. Import/Export/Reset/Undo are checked against their documented memory-versus-file behavior, not just their button receipts.
- For live Output, only a matching GUI worker ACK for the pending user may commit GUI settings. The GUI-local Apply test requires its recorded ACK for user A and exact settings. A connected B update requires a successful authenticated MCP result, last_error == null, exact B settings in that result and a fresh routing_state, and the GUI profile/committed snapshot updating to B. B’s independent pending local draft must remain present, A must stay unchanged, and an unrelated manual virtual F6 hold on B must survive until explicit release. The generic worker Event::Output state (acknowledged false, user null) is not evidence of the MCP command acknowledgement.
- The keyboardless virtual seat shows the key-output requirement and a disabled Save/Apply action. A synthetic physical-mouse seat shows the existing read-only unavailable explanation and disabled commit action. These fixtures use profile interface strings only and attach no physical device.
- Navigate all 13 Settings destinations once through the real category/destination controls. For each, return to Home, reopen Settings, and verify remembered category. Capture one representative Settings frame only. Verify Output Rules entered from Home automatically follows the selected B user without an output_user override, preserves the staged B draft on page return, and the route-12 Output Rules destination preserves that same stable identity. Existing five-category layout and Home framing remain closed unless the new originals expose a concrete regression.
- The four profile disclosures listed above are closed in the initial Profiles frame. Open only `Profile recovery` and `Automatic targeting scope` for focused checks; the canonical candidate evidence set contains six frames (two Output, two Profiles, one Automation minimum, one Settings), assembled from four unaffected first-run originals and two post-fix replacements. The layout qualification adds exactly those two replacement captures and no others. The baseline, if supplied, saves only four Output/Profiles render frames. Repeated or unchanged frames are not saved.

## Boundaries

The previously accepted compact Home/presentation, selected-user twelve-tab layout, Settings category rail/chooser, representative minimum forms, Output Rules native conversion and cleanup, profile-file maintenance, keyboard slider sample, and connected Agent grant mechanisms are reuse evidence. This pass does not certify every form field at once, full screen-reader support, all keyboard-navigation paths, broad Unicode, physical devices, arbitrary applications, injected desktop input, RustDesk, or complete MouseMux Ultra parity. Preserve all earlier failed/pending artifacts and their original verdicts.
