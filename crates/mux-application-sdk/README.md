# Rust cooperative application SDK adapter overlay

Private authoring only. No compiler, Cargo, rustfmt, tests, native process, browser, hardware, commit or push was executed by this author. This directory is a source overlay for a new crate; it does not modify the frozen 168-source candidate, existing workspace manifests, shared/public checkout or prior receipts. Source qualification and separate review remain with the root.

The crate consumes `mux-core::application_event` v2 and the independently authored `mux-windows::application_window::WindowAdapter`. New product behavior stays in Rust. Default features build the native local embedding/C ABI with optional Windows own-window integration. A browser/WASM crate should depend on this crate with `default-features = false`; its shared client state and protocol use no Windows provider or C ABI.

## Trust and authority

`Host` is a trusted in-process embedding object, confined to one UI thread with `!Send/!Sync`. It contains one cooperative engine and spawns zero threads/workers. `register_recipient`, `approve_events`, `approve_controls`, `create_owned_user`, `reset`, `end`, and `host_dispatch` are host setup/control boundaries. They must not be exposed as remotely callable client methods. Labels on these APIs are not an authentication/security boundary against arbitrary code already executing inside the embedding process.

`dispatch(bound_recipient, ClientRequest)` accepts an identity selected by the host/authenticated transport, outside the client JSON. `ClientCommand` has no host approval, recipient registration, native-handle registration or epoch-reset operation. Export consent alone grants no mutation: ControlGrant independently defaults off for lifecycle, cursor, pointer input, key input, tracking and window control. Existing core event grants remain independently enforced. AllOwned always means this actual recipient's users, not all session users. A key control needs both current key export/input consent and key control permission.

For the intended concurrent native + browser demonstration, create exactly two virtual users explicitly with trusted `Host::create_owned_user(local_owner, name)` or HostCommand::CreateUser. Native and browser consumers observe these same UserIds. Approve a browser Grant::Only of those IDs, then a separate ControlGrant::Only of those IDs with `delegated_users = true` and only the required operations enabled. `Host` privately records actual user ownership and resolves approved delegated controls to that owner before calling the unchanged core Engine. Cross-owner control additionally requires the caller's current per-user event/input grant. AllOwned, implicit access, or a missing delegated bit never authorizes another owner's user. The browser must not create two additional users to substitute for this design.

Each pressed key/button records the producer identity inside Host. Up from another producer is denied. Delegated event/control restriction and disconnect release only the delegate's own holds. Owner grant changes reconcile both core held state and the producer map; user disposal/owner disconnect/reset/end remove the map entries. This prevents a stale delegate cleanup from releasing a later owner's press. Mutations and cleanup are serialized on the owning UI thread. Control cleanup uses typed cooperative Up events; cleanup failure retires the host session.

Own-window operations remain restricted to actual native process/thread ownership. HostCommand::RegisterOwnWindow is a separate trusted native setup call; no client command accepts HWND/process IDs. The Windows backend initializes lazily and checks per-monitor DPI, window property cookies, process/thread/lifetime through the existing adapter. Non-Windows/disabled-feature builds report the backend unavailable. Native snapshots/controls do not carry raw handles. Host reset/end/drop retires the engine and native bindings; recipient disconnect retires its windows while leaving other consumers live when cleanup succeeds.

## Typed protocol and shared state

`ClientRequest {version, command}` returns `Reply<ClientResponse>` with status `ok` or `error`, version and typed data. An accepted input acknowledges cooperative publication, not target injection or delivery to an OS control. Poll batches are capped at 128; core queues remain capped at 4096.

`EventHello {version, credential}` is a separate initial event-transport frame with redacted Debug output. Its credential belongs only in transient memory; Origin must come from the HTTP upgrade, not client JSON. `Host::ready_for` exposes actual `EventReady` grants, control permissions, epoch, informational opaque recipient, capabilities and bounds. It does not create consent or credentials. ClientMessage carries a request ID and ClientRequest. ServerMessage has Ready, Response, EventStream(subscription, Poll) and Disconnected variants. The eventual server pushes only activity/gap/terminal streams; browser clients do not implement a 50 ms Poll RPC timer. Authentication, exact HTTP(S) Origin allowlisting, event-only credential issuance/expiry/revocation and transport lifetime remain root integration work.

`ClientState` (also exported as EventClientState) installs a validated Snapshot for an expected epoch supplied by the authenticated handshake, then folds Poll. Session-global sequences must strictly increase; skips are valid because events for other recipients are filtered. Only explicit Poll::Gap requests resubscription. Duplicate/reordered/version/epoch/invalid-input batches are transactional: no valid prefix commits, the previous watermark is retained, all users/windows/held state/cursors are cleared, and a fresh snapshot is required. End/disconnect and user disposal remove held state. Valid updates preserve complete cursor/color/render fields. Button membership uses identities, never assumed ordering. No extra sorting behavior was added; if an older core doc still promises canonical button order, update that doc to press order during root integration.

Screen/canvas transforms reuse the portable core contract and revisions. DOM-derived inputs use ClientCommand::InputAtRevision so the serialized host compares the measured transform revision against current screens before mutation; a stale revision returns StaleRevision. Native direct Input remains available. Trusted Host::update_screens / HostCommand::UpdateScreens wraps the existing core topology update without exposing it to clients. The client rejects stale input transform revisions, unknown users/sources, bad held transitions, invalid redaction combinations and oversized states. It does not infer browser mixed-DPI geometry. The expected epoch must come from trusted connection setup; accepting an arbitrary frame as the expected epoch would defeat stale-session protection.

## Native C ABI

Native exports use the same Host/Engine and JSON types. Rust build.rs generates `protoinputmultiplex_application_sdk.h` into Cargo OUT_DIR from typed Rust ABI metadata; no handwritten C++ logic or prebuilt header is included. `ffi::C_HEADER` exposes that generated header for packaging. Header generation occurs only when native-ffi is enabled. Root must copy the compiled generated header and matching library into SDK distribution outputs, and verify exported symbols and C/i686/x64 calling conventions.

The ABI has opaque globally unique numeric handles stored in a thread-local registry, never raw Rust object pointers. There are at most 16 hosts per thread, each with one pending response of at most 4 MiB. Requests are bounded to 64 KiB UTF-8 JSON, with serde's normal recursion limit. A wrong-thread or stale host handle is invalid. Every operation is synchronous on the creating UI thread. Reentrant access returns Busy. Host setup calls remain trusted local APIs; the bound recipient argument to client_call must be supplied by the host/transport, not taken from untrusted command JSON.

A call executes exactly once and queues its typed JSON reply. response_size inspects length; response_read copies and consumes only on success. BufferTooSmall writes the required length, preserves the same reply, and requires a copy retry rather than command re-execution. Another command while a reply is pending returns Busy. response_discard explicitly releases it. Scalar outputs require aligned writable storage; byte buffers are pointer+length, without trailing NUL; SDK retains no caller pointers. Non-NULL invalid memory/aliasing remains a C caller contract and cannot be validated by Rust. NULL and oversize requests are rejected before buffer reads.

Each export contains unwind panics. A caught panic retires and poisons the affected host; only destroy remains allowed. No callback unwinds across C. Panic=abort builds, OOM aborts, process termination and invalid caller memory are outside catch_unwind. The native registry itself spawns no worker and cannot move the !Send Windows adapter to another thread. The host must destroy all native handles on its UI thread before shutting it down.
